# R3 개인화·데이터 작업 지침

담당 **라즈**, 검토 **김동혁**. Jira [SCRUM-8](https://se4nchoi.atlassian.net/browse/SCRUM-8), 공동 검증 [SCRUM-14](https://se4nchoi.atlassian.net/browse/SCRUM-14). 권장 브랜치 `codex/scrum-8-personalization`. 이 문서는 구현 전 작업 계획이다. 인수인계 준비에서는 앱 코드를 바꾸지 않았으며, 아래 내용은 담당자가 자기 브랜치에서 수행할 과제다.

## 목표

전체 다섯 클래스가 있어야 사용 가능한 개인 모델을 **선택 동작 하나부터 검증해 사용할 수 있는 모델**로 바꾼다. 한 클래스만 있을 때도 다른 모양을 그 클래스라고 강제 분류하지 않는 거부 정책이 핵심이다.

## 파일 경계

- 주 담당: `src/personalization.js`의 특징·품질·모델·분류·검증.
- 시험: `tests/personalization.test.js`, `scripts/probe-personalization.mjs`, 수집 규격 문서.
- R1 협의: 좌표·종횡비·손 정보·기울기. R4 협의: 동작별 표본과 별도 확인. R5 협의: `validateProfile` 변경·부분 저장·버전.
- `src/enrollment.js`는 R4, `src/profile-store.js`와 `src/app.js`는 R5 소유다.
- 제안 산출물: `docs/evidence/r3-data-spec.md`, `docs/evidence/r3-evaluation.md`.

## 순서

1. 현행 `POSES`, `trainEnvironment`, `modelValid`, `classifyPersonal`, `validateProfile`의 전체 클래스 가정을 목록화한다.
2. 실물 실패 로그에서 품질 보류·각도 조건과 모델 구성 실패·클래스 충돌·확인 실패를 분리한다. 등록 실패를 모두 데이터 부족으로 단정하지 않는다.
3. R4·R5와 [단일 동작 계약](../contracts.md)을 확정하고 후보 학습, 충돌 점검, 검증 결과 스키마를 계약 테스트로 만든다.
4. 기본 동작 한 개만 있는 모델부터 지원한다. 긍정 클래스가 하나일 때 두 번째 후보 마진은 없으므로 `null`로 취급하고, 거리·거부 예시·미관찰 영역 시험으로 수락을 제한한다.
5. 새 동작을 추가할 때 기존 활성 클래스와 충돌 검사한다. 실패하면 후보만 보류하고 기존 모델을 바꾸지 않는다.
6. 구형 모델 v1/v2와 특징 버전의 읽기·변환을 R5와 시험한다. 임의 ID는 P1에서 도입하되 P0 설계가 고정 라벨에 다시 묶이지 않게 한다.
7. 등록과 별도 세션으로 단일 등록·추가 등록의 명령 성공, 다른 모양 거부, 사용자·환경별 혼동을 평가한다.

## 데이터·거부 계약

한 클래스의 표본에 가까운지를 확인하는 것과 어떤 미등록 모양도 거부한다는 것은 다르다. 타이핑·손 쉬기·물건 잡기·다른 손 모양을 포함한 별도 거부 시험이 필요하다. 필요한 거부 증거가 없으면 명령 활성화를 보류한다. 다른 네 동작 전체를 다시 강제 등록하게 만들지 않는다.

- 새 특징은 유한성·길이·범위를 검증한다. 입력 크기·미러링 변화의 영향을 확인한다.
- 여러 각도 분포를 한 평균으로 뭉개지 않는다. 각도 수·시간을 줄이는 경우 미수집 방향의 행동을 명시한다.
- 수집 예시, 별도 확인, 최종 평가 세션을 구분한다. 같은 영상의 이웃 프레임을 독립 시도로 세지 않는다.
- `rock`은 사용자 예시를 새 ID로 보존하는 P1 사례다. 기존 공통 모델이 특정 라벨을 출력해야 등록되는 조건을 붙이지 않는다.
- 사전학습 모델 가중치를 갱신하지 않는 한 파인튜닝 성과로 표현하지 않는다.

## 검증과 인수

```powershell
node --test tests/personalization.test.js tests/profile-store.test.js
```

`scripts/probe-personalization.mjs`는 숫자 fixture를 재생성하여 덮어쓰는 조사 도구다. 일반 회귀 시험이나 설치 확인에서 실행하지 않는다. R3이 의도적으로 fixture를 갱신할 때만 입력·모델 버전·출처와 변경 diff를 확인하며 실행한다. 합성 특징 성공을 실제 사람의 성공률로 쓰지 않는다.

- 하나의 유효 클래스만 등록해도 구조가 유효하고 해당 클래스만 활성화된다.
- 미등록·중립·범위 밖·경쟁 클래스 충돌을 이유 코드로 거부한다.
- 표본 부족·비유한 입력·특징 버전 불일치를 명시적으로 처리한다.
- 클래스 추가 실패가 기존 클래스를 삭제하거나 조용히 비활성화하지 않는다.
- 구형 프로필·모델과 부분 등록이 R5 저장 시험을 통과한다.
- 별도 세션의 참가자·환경·시도 수, 혼동과 오실행 결과를 남긴다.
