# 확장 검토: 웹캠 시선 추적 + 손은 "액션"만 맡기는 구조

- **작성:** 2026-11-04, MANUX Discord 협업 세션(AI 초안, 사람 검수 전)
- **전제 문서:** [웹캠 손 인터페이스 타당성 조사](webcam-input-feasibility.md)
- **질문(sean.choi):** 같은 웹캠 이미지로 아이트래킹을 구현하고 손은 클릭·스크롤 같은 액션으로 제한하면 어떤가
- **근거:** 웹 검색 요약 위주(논문 본문은 읽지 못함)와 제가 계산한 값. 저장소는 `origin/preview` 파일을 읽은 것이고 시선 추적은 **구현·측정하지 않았습니다.**
- **표기:** `확인`=공식 문서에서 직접 확인, `요약`=검색 요약만 확인, `계산`=아래 가정으로 제가 계산, `추론`=제 해석, `미확인`=근거 못 찾음

## 0. 결론

| 구조 | 판정 | 이유 |
| --- | --- | --- |
| **B. 시선만으로 커서 + 손은 클릭·스크롤** (Vision Pro 방식) | **현재 일반 웹캠으로는 어렵다** | 웹캠 시선 오차 보고치가 약 2~4°. 일반 모니터에서 150px 안팎이라 Windows 아이콘·버튼(수십 px)을 못 맞춘다(`계산`) |
| **A. 시선은 "대략 어디"만, 손이 미세 조정** (MAGIC pointing 계열) | **가장 유망하지만 연구급 위험** | 먼 거리 이동을 시선이 대신해 팔 이동이 줄고, 미세 조작은 손이 맡는다. 시선 정확도와 드리프트가 성패를 가른다 |
| **C. 시선은 "화면을 보고 있나"만** (참여 상태) | **가장 안전하고 바로 가치 있음** | 정확도 요구가 낮다. 딴 곳을 볼 때 손 명령을 막아 오실행을 줄인다 |
| **D. 지금처럼 손 위치로 커서** (기준선) | 유지 | 시선 실험의 비교 기준이 된다 |

**권고(추론):** B는 지금 하지 않는다. **C를 먼저 시험하고, A는 계약에 확장 자리만 남긴 뒤 소규모 실측으로 가부를 정한다.** 손 기반 기준선(D)은 바꾸지 않는다.

## 1. 시선 추적이 해결해 주는 것, 못 해주는 것

| 우리 문제 | 시선이 도움이 되나 | 설명 |
| --- | --- | --- |
| 펼친 손 등 큰 동작이 피로함 | **도움됨(구조 B·A)** | 손이 위치를 맡지 않으면 큰 팔 이동이 사라진다. 손을 책상·무릎에 두고 핀치만 해도 된다. 팔 지지 시 부담이 줄어든다는 연구와 같은 방향([Consumed Endurance 2014](https://blog.jhincapie.com/wp-content/uploads/2010/02/ga-final.pdf), 요약) |
| 관절 겹침으로 인한 커서 jitter | **일부 도움됨** | 커서가 손 좌표에서 떨어지므로 손 떨림이 커서를 직접 흔들지 않는다. 다만 **눈 추정 자체의 잡음**이 새로 생긴다(`추론`) |
| 핀치 판정이 가림에 약함 | **도움 안 됨** | 클릭이 여전히 손가락 접촉이다. 엄지가 검지 뒤로 숨는 문제는 그대로 |
| 2D 깊이 모호성 | **해당 없음** | 시선 문제는 다른 종류의 모호성(머리 자세·홍채 크기)을 가진다 |

즉 **피로와 커서 jitter는 줄 수 있어도, 클릭 오인식은 못 줄인다.** 이 점은 "손은 액션만"이어도 손가락 판정 품질은 그대로 숙제라는 뜻입니다.

## 2. 웹캠 시선 추정의 정확도 근거

| 근거 | 내용 | 상태 |
| --- | --- | --- |
| WebGazer 원 논문 | 상용 아이트래커와 비교한 평균 오차 **약 4.17°** ([IJCAI 2016](https://jeffhuang.com/papers/WebGazer_IJCAI16.pdf)) | 요약 |
| 학생 논문(Utrecht) | WebGazer 약 **3.65°**, 정밀도(RMS) 0.89°, **실험 중 드리프트로 정확도 하락**, 사후 보정 시도는 실패 ([thesis](https://studenttheses.uu.nl/handle/20.500.12932/40709)) | 요약 |
| Tobii 4C 비교 논문 | "정확도·신뢰성이 필요한 작업에는 WebGazer 부적합"이라는 결론 | 요약 (한 출처에서 인용) |
| 신규 방법(UNL 학위논문) | 통제 조건에서 중앙 오차 **약 2°**, 머리 자유 이동에서도 WebGazer보다 1° 이상 우수 ([UNL](https://digitalcommons.unl.edu/computerscidiss/255)) | 요약 |
| MPIIGaze 계열 | 교차 데이터셋 평균 오차 10.8~13.9°. 개인화 방법(SPAZE)은 MPIIGaze에서 **2.70°** ([MPIIGaze](https://ar5iv.arxiv.org/html/1711.09017), [개인화](https://alphaxiv.org/abs/1807.00664)) | 요약. 개인화·교정이 정확도를 크게 좌우 |
| 머리 움직임 | 교정 뒤 머리를 움직이면 오차가 늘고, 살짝 기울기만 해도 드리프트가 생긴다는 벤더 설명 ([Smart Eye](https://smarteye.se/blog/why-eye-tracking-calibration-fails-and-how-to-get-it-right-in-the-real-world/)) | 요약(벤더 글) |
| 조명·안경 | 안경 반사가 주된 문제, 교정 때와 다른 조명에서 오차 증가 | 요약(벤더 글) |
| 적외선 전용 기기 기준점 | Tobii Pro X3-120은 이상 조건에서 양안 0.4° ([사양표](https://manualshive.com/en/manual/tobii-pro/x3-120/1124409?page=6)). 소비자용 Eye Tracker 5는 정확도 수치를 못 찾음 | 요약 / 미확인 |

**주의:** 위 수치는 서로 다른 장비·과제·조건이라 직접 비교할 수 없습니다. 2024~2025년 체계적 리뷰는 찾지 못했습니다. 우리 웹캠·조명에서의 값은 **측정 전에는 모릅니다.**

### 2.1 화면에서 몇 픽셀인가 (`계산`)

가정: 시청 거리 60cm, 24인치 16:9(약 53×30cm), 1920×1080(약 36px/cm). 1° ≈ 1.05cm ≈ **38px**.

| 시선 오차 | 화면상 오차(약) | 비교 |
| --- | --- | --- |
| 0.4° (적외선 전용 기기 이상 조건) | 15px | 아이콘(약 32~48px) 안에 들어감 |
| 2° (신규 방법의 통제 조건) | 76px | 아이콘보다 큼, 큰 버튼 수준 |
| 3.65° (학생 논문 WebGazer) | 약 140px | 창 제목줄 높이의 3~4배 |
| 4.17° (WebGazer 원 논문) | 약 160px | 화면 높이의 약 15% |

→ **시선만으로 일반 Windows UI의 작은 대상을 정확히 가리키는 것은 일반 웹캠으로는 어렵다**(`계산`+`추론`). Vision Pro가 시선을 쓰는 것은 적외선 눈 카메라와 큰 대상의 UI 설계가 함께 있기 때문입니다(`추론`, [UploadVR](https://uploadvr.com/apple-vision-pro-gesture-controls) 요약).

## 3. 구조별 상세

### 3.1 구조 B: 시선 커서 + 손 액션

| 장점 | 위험 |
| --- | --- |
| 손을 쉬는 자세(책상·무릎)에 둘 수 있어 피로 감소 가능 | 위 계산처럼 **정밀도 부족** |
| 손 위치 jitter와 커서 분리 | **Midas touch**: 보는 것만으로 의도치 않게 선택되지 않게 해야 함. Vision Pro는 핀치가 인식될 때만 시선을 쓴다 |
| Vision Pro·HoloLens 같은 "point and commit" 원칙과 일치 | 눈은 원래 훑어보는 기관이라 클릭 대상 고정에 부적합하다는 비판([Skarredghost](https://skarredghost.com/2024/02/08/apple-vision-pro-ux-interface/), 요약) |
| | 교정 필요, 머리 움직임·조명·안경 영향, 드리프트 |

### 3.2 구조 A: 시선으로 접근, 손으로 미세 조정 (MAGIC pointing)

- 원 연구(Zhai 등, CHI 1999): 시선이 커서를 목표 **근처로 이동**시키고 최종 선택은 수동 입력. 보수형은 **손 움직임이 시작될 때만** 커서를 시선 쪽으로 옮긴다. 신체 부담은 줄고 시선 단독보다 정확·자연스럽다고 보고([설명 자료](https://www.cs.princeton.edu/courses/archive/fall08/cos436/Zhai/magic.pdf), 요약).
- 알려진 문제: **오버슈트**(손이 이미 움직이는 중에 커서가 이동), **시선 정확도가 낮으면 엉뚱한 방향으로 안내**. 후속 연구(Magic-Sense 등)는 시선 근처에서 감도를 낮춰 미세 선택을 돕는다(요약).
- **우리에게 맞는 점:** 시선 오차 2~4°(76~160px)를 손의 **미세 이동 범위 안**에서 흡수하면 된다. 합격선은 `시선 오차(px) < 손 미세 이동이 감당하는 반경`(팀이 정함, 이 문서는 수치를 제안하지 않음).
- **필요한 설계:** 손이 움직이기 시작하는 순간에만 워프(보수형), 워프 거리 상한, 워프 직후 손 상대 이동으로 즉시 전환, 시선 불확실 시 워프 금지.

### 3.3 구조 C: 시선은 참여 상태만

- "화면을 보고 있는가/타이핑 중인가"만 알면 된다. 손 명령을 **보고 있지 않을 때 무시**해 오실행을 줄인다. 저장소의 `docs/m1-webcam-mouse/posture-and-engagement.md`가 이미 "타이핑·읽기와 제어의 경계"를 다룬다.
- 정확도 요구가 낮아 머리 자세(MediaPipe Face Landmarker의 변환 행렬 출력, `확인`)만으로도 일부 가능(`추론`).

## 4. 같은 웹캠 영상으로 가능한가 (구현 측면)

| 항목 | 내용 | 상태 |
| --- | --- | --- |
| 얼굴 모델 | MediaPipe Face Landmarker가 478점 3D 얼굴 랜드마크, 선택 출력으로 52 블렌드셰이프와 **얼굴 변환 행렬**을 제공 | `확인`([공식](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker)) |
| 홍채 포인트 | 478점은 홍채를 포함하는 구성으로 알려져 있으나, 이번 문서 발췌에서는 명시적으로 확인하지 못함 | `미확인` |
| 시선 방향 | MediaPipe는 시선 각도를 **직접 출력하지 않는다**(제가 본 문서에는 없음). 홍채 위치+머리 자세로 직접 계산하거나 별도 시선 모델이 필요 | `추론` |
| 모델 2개 동시 | 손 모델과 얼굴 모델을 같은 프레임에서 돌린다. 저장소 계약은 "동시에 한 프레임"이라 **총 지연이 늘어난다**. 크기·지연은 측정하지 않음 | `미확인` |
| 해상도·위치 | 웹캠이 책상 위 정면이면 눈은 잘 보이고 손은 아래쪽 가장자리에서 가려질 수 있음. **한 카메라로 두 목적의 배치가 충돌**할 수 있음 | `추론` |
| 런타임 | 두 앱 모두 MediaPipe 사용(Electron은 JS, Python 앱은 Tasks). 얼굴 모델도 두 환경에 있음 | `추론` |

특히 **카메라 배치 충돌**이 중요합니다. 시선은 얼굴을 정면에서 보는 위치가 유리하고, 손 추적은 손이 시야 안에 있는 위치가 유리합니다. 한 개의 일반 웹캠으로 둘을 동시에 만족하는 배치는 **실측해야** 압니다.

## 5. 우리 구조에 넣는다면

저장소의 7개 컴포넌트 중 **추적**에 얼굴 입력이 추가되고, 기반 계약에는 아래 확장 자리만 둡니다.

```
FaceState (추적 계층, 신규 제안)
  t, faces[]            얼굴 랜드마크, 머리 자세(변환 행렬)
  gaze                  { point: 화면 0..1 | null, uncertainty_px, valid }
  attending             bool       # 화면을 보고 있는가 (구조 C)

PointerSignal 확장
  source                'hand' | 'gaze-warp'
  warp                  { to: 화면 좌표, reason, gaze_uncertainty_px }   # 구조 A에서만

IntentEvent
  (변경 없음)  # 손은 press/release/click/scroll 같은 사건만 낸다
```

- `OutputAction` 4종(move/button/scroll/release)과 안전 해제 계약은 **그대로** 둔다.
- 시선 값이 `valid:false`이면 **손 기준선(D)으로 자동 복귀**한다. 시선 실패가 입력 전체를 막지 않게 한다(저장소의 "안전 쪽 실패" 원칙).

## 6. 시험 계획 (가부 판단용, 구현 전 단계)

| 단계 | 내용 | 산출물 |
| --- | --- | --- |
| 1. 정확도 측정 | 9점 또는 16점 교정과 별도 검증점으로 **각도(°)와 px** 측정. 팀원 3명 이상, 안경 유무, 머리 고정/자유, 조명 2종, **10분 뒤 드리프트** | 조건별 오차 표 |
| 2. 카메라 배치 | 손과 눈이 동시에 충분히 보이는 높이·각도 탐색 | 권장 배치 |
| 3. C 시험 | "화면을 보지 않을 때 손 명령 무시"만 구현해 오실행 감소 비교 | 오실행 횟수 비교 |
| 4. A 프로토타입 | 보수형 워프, 이동 거리 상한, 손 미세 이동. 기준선 D와 같은 과제 비교 | 이동 시간·오실행·피로(자기 보고) |
| 5. 판단 | 1단계의 오차(px)가 손의 미세 이동 반경 안에 들어오는지 | go / no-go |

- 평가는 **사용자 시도 단위로 분리**하고(같은 시선의 인접 프레임은 독립 시도가 아님), 교정과 평가를 같은 데이터로 하지 않는다.
- **개인정보:** 얼굴·눈 영상과 시선 좌표는 민감한 생체 정보다. **로컬 처리만, 원시 영상·좌표 기록은 저장소에 넣지 않고**, 기록이 필요하면 참가자 동의와 익명화를 거친다.

## 8. 한계

- 시선 정확도 수치는 **다른 조건의 연구들을 검색 요약으로 모은 것**이고, 우리 환경 값이 아닙니다. 논문 본문은 읽지 못했습니다.
- 픽셀 환산은 제가 가정한 모니터·거리 기준 계산입니다.
- MediaPipe의 홍채 포인트와 시선 출력 여부는 이번 문서 발췌로 확정하지 못했습니다.
- 두 모델 동시 실행의 지연·부하는 측정하지 않았습니다.
- 구조 A의 효과는 원 연구(1999)와 후속 연구의 요약에 의존하며, 웹캠 오차 수준에서 같은 효과가 나는지는 **미확인**입니다.
- 건강·피로 효과(터널증후군 포함)는 이 구조에서도 **주장할 근거가 없습니다.**
