# MANUX에서 취업 준비로 가져갈 역량과 증거

작성일: 2026-10-29. 아래 우선순위는 이 프로젝트에서 **실제로 설명하고 증명하기 좋은 순서**다. 채용 공고의 요구 빈도나 합격 가능성을 추정한 순위가 아니다. 현재 코드, 이번 각도별 등록 개선, 향후 Electron·OS 연동을 구분한다.

## 현재 상태를 구분해서 말하기

| 구분 | 설명할 수 있는 범위 |
| --- | --- |
| 현재 공통 프로토타입 | 로컬 카메라·Worker 추론, 한 프레임만 처리, 비동기 종료 처리, 특징 기반 개인화, 명령 상태·선택적 반복, 프로필 저장, 브라우저 시험 |
| 이번 각도별 등록 개선에서 증명할 것 | 각도 추정과 충족 판정, 충분한 유효 관찰, 방향별 진행 표시, 여러 각도의 분류 모델, 학습과 별도 확인의 분리 |
| 향후 직접 구현한 뒤 주장할 것 | Electron IPC·네이티브 경계, 사용자 정의 gesture ID와 바인딩, OS 액션·매크로 실행, 설치 패키지·다른 PC 검증 |

공통 프로토타입에 존재하는 기능을 개인의 독자 성과로 바꾸어 적지 않는다. 본인이 이해하고 수정한 범위, 설계 선택, 검증 결과를 연결해 설명한다. 아직 실측하지 않은 수치는 이력서의 성과 수치로 쓰지 않는다.

## 핵심 역량과 다른 분야에서의 재사용

| 핵심 역량 | 이 프로젝트에서 배울 내용 | 다른 분야에 옮겨 쓰는 이유 | 남겨야 할 증거 |
| --- | --- | --- | --- |
| 문제를 측정 가능한 실험으로 바꾸기 | “인식이 흔들린다”를 손 검출 실패·동작 혼동·오실행·지연으로 나누고 조건을 고정 | 추천·검색·이상 탐지·제품 성능 개선에도 같은 문제 정의와 비교 설계가 필요 | 기준선, 실패 분류표, 실험 조건, 전후 결과와 원시 로그 |
| 데이터 수집·평가 설계 | 같은 자세의 이웃 프레임 수와 독립된 시도 수 구분, 각도·사용자·세션 분리, 등록/시험 누수 방지 | ML 데이터셋·센서 분석·A/B 실험에서 결과 신뢰도를 결정 | 수집 규격, 분할 기준, 혼동 행렬, 무명령 구간 오실행/분 |
| 실시간 비동기 시스템 | Worker, 한 프레임 처리와 오래된 입력 누적 방지, 종료 토큰, 늦은 응답 무시, 자원 정리 | 영상·음성·IoT·로봇·실시간 UI의 지연과 경쟁 상태에도 적용 | 시간순 로그, 재현 스크립트, 중단·재연결·timeout 회귀 시험 |
| 상태 머신과 이벤트 설계 | 후보·확정·유지·해제·반복·취소를 분리하고 불확실한 프레임에서 실행하지 않기 | 결제·업로드·장치 제어·워크플로의 상태 전이와 복구에 적용 | 상태 전이도, 입력 시퀀스, 경계 조건 시험, 반복 중단 사례 |
| 특징 표현과 모델 선택 | 회전에 강한 관절 특징, 방향을 명령으로 쓸 때의 별도 표현, 거리 기반 거부, 여러 각도 보존 | 분류·매칭·검색에서 무엇을 같게 보고 무엇을 구분할지 설계하는 능력 | 특징 정의, 비교 모델, 실패 사례, 거부 기준 선택 근거 |
| UX와 내부 상태의 관찰 가능성 | 카메라·수집 수·부족한 각도·보류 이유를 보여주고 실패를 재시도하게 만들기 | 설정·연결·업로드·AI 결과 검토 등 사용자가 기다리고 수정하는 흐름에 적용 | 온보딩 완료 시간·재시도, 화면 기록, 사용자 관찰과 수정 내역 |
| API·프로세스·네이티브 경계 | 향후 gesture event→binding→허용 IPC→Windows action 계약, 인자 검증, 결과·취소 처리 | 웹/서버·플러그인·하드웨어·데스크톱 연동에서 권한과 책임 경계를 설계 | 스키마, IPC 계약 시험, 잘못된 요청 거부, 실제 OS 실행 결과 |
| 협업과 재현 가능한 통합 | 담당 모듈 API 합의, 변경 리뷰, 시험 데이터 공유, 다른 PC 실행 | 언어·프레임워크가 바뀌어도 팀 개발에서 반복되는 요구 | PR·리뷰·계약 변경 기록, 재현 명령, 통합 실패 수정 과정 |

가장 강한 공통 역량은 **문제 정의 → 데이터/측정 → 구현 선택 → 비교 검증**의 한 사이클을 끝내는 능력이다. “MediaPipe를 사용했다”라는 도구 이름보다, 어떤 실패를 발견했고 무엇을 바꾸어 어떤 조건에서 개선됐는지를 설명하는 것이 구체적이다.

## 지표를 섞지 않기

- 프레임 분류 점수는 인식 정확도 백분율이 아니다.
- 사용자가 한 번 유지한 손에서 100개 프레임이 나와도 명령 시도 100회로 세지 않는다.
- 추론 시간, 결과 도착 간격, 후보→명령 지연, 사람의 동작→실제 화면 반응 시간은 다르다.
- 성공률과 함께 무명령 구간 오실행, 반복 중단 실패, 등록 실패를 기록한다.
- 중앙값과 p95에는 표본 수와 조건을 붙인다. 개선 후 설정을 골랐다면 별도 세션으로 다시 평가한다.
- 정적 사진·합성 카메라 시험은 기능 통합 증거다. 실제 사용자·거리 성능 증거는 별도다.

현재 GPU/CPU 벤치와 합성 카메라 검증 기록은 실험 도구의 출발점이다. 이 결과를 실제 소파 사용 성능으로 확대해서 표현하지 않는다. 상세 기준은 [팀 평가 계획](team-plan.md), 현재 검증은 [검증 기록](verification.md)을 참조한다.

## 5명에게 가장 강하게 남길 역량

| 담당 | 집중할 1~2개 역량 | 본인의 완성 과제 |
| --- | --- | --- |
| R1. 비전·카메라·성능 | 실시간 비동기 처리, 성능 분석 | 해상도별 속도·손 검출·기울기 추정을 비교하고 연결 종료·재연결·늦은 결과를 처리 |
| R2. 동작 판정·명령 제어 | 상태 머신, 지연·오실행 절충 | 진입·유지·해제·반복 조건을 설계하고 흔들리는 입력과 명령 전환을 재현 시험 |
| R3. 개인화·데이터 | 특징 표현·모델 선택, 데이터 평가 설계 | 같은 각도와 여러 각도의 등록을 비교하고 다른 동작·무명령을 거부하는 기준을 검증 |
| R4. 등록·제품 UI | UX 관찰 가능성, 실패 복구 흐름 | 사용자가 각도별 등록·별도 확인·재시도를 스스로 완료하도록 만들고 완료 시간과 실패를 측정 |
| R5. 프로필·통합·실행 | 데이터 버전 호환, API 계약·재현성 | 저장·복원·설정 전환을 연결하고 다른 PC 실행과 평가 로그·결과 집계를 재현 가능하게 함 |

현재 담당 배분은 [팀 개발·평가 계획](team-plan.md)의 R1~R5와 맞춘다. R5가 평가 통합을 맡더라도 모듈별 검증 도구, 실물 시험과 실패 원인 수정에는 전원이 참여한다. 향후 Electron·OS 연동을 맡는 사람은 프로세스·네이티브 경계와 권한 설계 역량까지 확장할 수 있다. 해당 코드를 실제 구현하기 전에는 계획과 구현 경험을 구분한다.

## 면접에서 설명할 수 있는 문장 구조

다음 문장은 **직접 작업하고 확인한 부분만 선택해 완성할 예시**다. 괄호에는 실제 조건·수치를 넣고, 수치가 없으면 발견·설계·검증 범위까지만 말한다.

> “등록 표본 수는 충분해도 같은 각도의 비슷한 프레임만 모이는 문제를 발견했습니다. 각도별 수집 충족 조건을 추가하고 등록과 다른 세션으로 평가해, [사용자 수·조건]에서 [성공률/등록 실패] 변화를 확인했습니다.”

> “영상 추론 결과가 늦게 도착해 이전 상태에 명령을 보내는 경쟁 조건을 다뤘습니다. 동시 처리 프레임을 제한하고 세션·이동 세대 번호를 확인하게 바꾼 뒤, 종료·즉시 재등록·늦은 오류를 재현하는 시험으로 확인했습니다.”

> “유지 시간만 줄이면 오실행이 늘 수 있어 진입/유지 문턱과 명령 상태를 분리했습니다. [무명령 시나리오]와 [전환 시나리오]를 같은 조건으로 비교하고 지연과 오실행을 함께 기록했습니다.”

> “향후 Electron 구현에서는 UI가 임의 시스템 명령을 호출하지 않도록 액션 ID·허용 인자만 넘기는 API를 만들었습니다. [실제 지원 액션]에 대해 [잘못된 요청·취소·권한 실패]를 시험했습니다.”

마지막 예시는 미래 구현을 완료한 뒤 사용할 수 있다. 현재 개인화는 사전학습 모델의 가중치를 갱신하지 않으므로 “모델을 파인튜닝했다” 대신 **“관절 특징 기반 개인화 분류와 거부 판정을 설계·검증했다”**처럼 실제 수행 범위를 표현한다. 기술 구분은 [데스크톱 HMI 설계](desktop-hmi.md)에 정리했다.

## 2주 동안 증거를 남기는 방법

| 시점 | 남길 증거 |
| --- | --- |
| D1~2 | 본인 담당 실패 사례 1~2개, 재현 절차, 기준선 로그, API 계약, 비교 조건·지표 |
| D3~6 | 설계 근거와 코드 PR, 동료 리뷰, 재현 시험, 조건을 바꾸지 않은 중간 비교 |
| D7~8 | 등록과 분리된 실제 수행 세션, 사용자·장치별 결과, 실패 예시와 수정 후 재평가 |
| D9~10 | 다른 사람이 실행 가능한 명령·데이터 설명, 본인 담당 시연, 1쪽 결과표, 알려진 한계 |

개인 포트폴리오에는 **문제 1개를 깊게 해결한 사례 1~2개**를 우선 넣는다. 저장소 경로·PR·재현 스크립트·결과표를 연결하고, 공통 코드와 본인의 변경을 구분한다. 줄 수나 커밋 수를 늘리는 작업보다 설계 판단과 검증 근거를 남기는 데 시간을 쓴다.
