# 조작 자세와 제어 참여 상태의 설계

웹캠으로 마우스를 대체한다는 요구가 손을 계속 공중에 들어야 한다는 뜻은 아니다. 어떤 손모양을 사용할지 정하기 전에 **몸을 어디에 지지하고, 언제 손 움직임을 입력으로 연결할지**를 검토한다. 아래는 새로운 제품 기능의 결정이나 구현이 아닌 비교할 설계 축이다.

우선 사용 환경은 2026-11-03 사용자가 확인한 **책상에서 일반 PC 작업**이다. 팔을 편하게 둘 수 있는지와 키보드 왕복을 중심에 두고 자세·참여·재배치를 비교한다. 한 손/두 손이나 정확한 카메라 배치는 아직 선정하지 않았다.

## 자세를 먼저 검토할 이유

| 자세 후보 | 기대할 수 있는 이점 가설 | 확인할 제약 |
| --- | --- | --- |
| 팔을 낮게 두고 작은 공중 움직임 | 손 위치가 보이면서 큰 자세 변경을 줄일 가능성 | 계속 들고 있을 때 부담, 일반 웹캠 시야, 키보드 복귀 |
| 전완이나 팔꿈치를 지지하고 손만 움직임 | 어깨 지지 부담을 줄이고 작은 조작 범위를 만들 가능성 | 손목·손가락에 부담이 옮겨지는지, 좁은 범위의 정밀도·재배치 |
| 책상 가까이에서 손을 지지하거나 미끄러뜨림 | 물리적 기준과 키보드 가까운 조작 영역을 이용할 가능성 | 손등·가림·웹캠 각도, 마찰과 이동 범위, 실제 접촉을 알 수 있는지 |

이 세 가지를 손 수·클릭 방식·필터까지 모두 교차한 큰 실험으로 만들지 않는다. 사전 몸동작 검토에서 편한 범위와 카메라가 볼 수 있어야 하는 영역을 정의하고, 실제 센서 평가에서 그 조건을 별도로 확인한다. 몸동작 시연만으로 카메라 추적 가능성을 통과시켰다고 판단하지 않는다.

Consumed Endurance 연구의 해당 조건에서는 팔을 굽히고 어깨와 허리 사이 높이에서 조작하는 편이 부담 지표에 유리했다. 이는 모든 책상 높이와 지지 자세가 편하다는 증명이 아니다. [원문](https://blog.jhincapie.com/wp-content/uploads/2010/02/ga-final.pdf)

Keyboard Surface Interaction 연구는 키보드 위에서 포인팅과 타이핑을 가까이 배치하는 발상을 평가했다. 마우스보다 손을 옮기는 시간이 줄고 불편감이 낮았지만 목표까지 움직이는 시간은 길었다. 최종 비교는 IR 표식·Wii Remote 기반 절대 좌표 추적과 키보드 입력을 사용했다. 일반 RGB 웹캠의 맨손 상대 이동이나 손 제스처 클릭이 검증된 결과로 해석하지 않는다. [저자 원문](https://www.julian-ramos.com/papers/Ramos2016.pdf)

따라서 **지지 자세, 좌표 매핑, 접촉 판정, 클릭 방법**은 각각 평가한다. 손이 책상에 닿았는지와 화면에서 손을 찾았는지는 다른 사실이다. RGB 웹캠만으로 실제 접촉을 확실히 알아낸다는 전제는 두지 않는다.

## 자세 유지 요구를 없애도 참여 경계는 필요하다

단계형 이동이 켜진 뒤 손가락을 자유롭게 움직일 수 있더라도, 사용자가 읽기·타이핑·컵 들기로 전환하면 그 손의 움직임이 커서 이동이나 hover로 전달될 수 있다. 클릭 오실행이 없다는 사실만으로 이 문제가 해결되지 않는다.

| 참여 관리 후보 | 사용자 경험 | 반증할 질문 |
| --- | --- | --- |
| 명시적 시작과 쉬기 | 한 번 시작하고 편하게 이동하다가 스스로 쉬기 요청 | 사용자가 종료를 자주 잊는가? 타이핑 왕복마다 부담스러운가? |
| 조작 영역과 휴식 영역 | 편한 공간 안에서 이동하고 휴식 영역으로 옮겨 입력 분리 | 자연스러운 손 이동이 경계를 자주 넘는가? 웹캠이 두 영역을 볼 수 있는가? |
| 잠깐 끊는 재배치 신호 | 커서를 고정하고 손 위치를 다시 잡음 | 신호 자체를 계속 유지하는 부담이 새로 생기는가? 재개를 잊는가? |
| 다른 손으로 참여 요청 | 이동 손의 자세를 덜 바꾸고 보조손으로 켜기·쉬기 | 한 손을 키보드에 쓸 수 있는가? 양손 가림·복귀 부담이 더 큰가? |

어느 후보도 자세 분류를 매 프레임 통과시키는 기존 조건을 몰래 되살리는 방식으로 채택하지 않는다. 반대로 제어 모드를 영구히 기억하는 것만으로 일상 행동을 구분할 수 있다고 가정하지도 않는다. 참여 상태가 사용자에게 보이고, 켜기·쉬기·다시 시작의 비용이 감당 가능한지를 평가한다.

## 먼저 따라가 볼 장면

1. 이동을 시작하고 목표를 한 번 고른 뒤 그대로 문서를 읽는다.
2. 손이 화면에 남아 있는 채 문장을 타이핑한다.
3. 제어를 끄는 것을 잊고 컵을 들거나 얼굴을 만진다.
4. 손이 조작 영역의 가장자리에 도달해 편한 위치로 되돌린다.
5. 팔을 지지한 자세에서 짧은 클릭과 긴 드래그를 번갈아 한다.
6. 의자에 기대고 다시 앞으로 앉은 뒤 조작을 재개한다.

이때 의도하지 않은 커서 변위·hover와 클릭·스크롤을 구분해 기록한다. 휴식을 잊은 횟수, 쉬기·재진입에 걸리는 동작 수, 어깨·팔·손목·손가락의 부담, 카메라 가림을 함께 본다. 큰 움직임이 적었다는 이유만으로 손목·손가락의 부담이 적었다고 판정하지 않는다.

## 검토 순서

사전 검토에서 주 사용 환경과 편한 자세·시야 가정을 정한다. 그 조건에서 B1/B2의 동작 문법을 선별하고, 같은 문법을 쓰는 한 손·두 손을 비교한다. 이후 실제 웹캠에서 추적·접촉·종단 지연을 평가한다. 지지 여부·감도·영역·클릭 방식이 모두 달랐다면 결과를 손 개수나 단계형 하나의 효과로 귀속하지 않는다.

특정 자세가 기본값으로 채택되기 전까지 상대 이동과 절대 이동도 미결정이다. 상대 이동은 넓은 화면 이동과 재배치를 다루고, 절대 이동은 대응 관계와 전체 작업 영역을 다룬다. 둘 중 하나의 장점을 자세 지지 효과와 섞어 판단하지 않는다.

## 타이핑과 포인팅의 왕복

책상 작업에서는 목표를 누르는 구간뿐 아니라 **텍스트 필드 선택 → 입력 → 다른 목표 선택 → 입력**의 전체 흐름이 중요하다. 손을 키보드 가까이에 두더라도 쉬기·시작 요청이 잦으면 이득이 줄 수 있다. 이는 설계 가설이며 웹캠 방식의 측정 결과가 아니다.

Fingers/KSI 연구는 손을 옮기는 구간과 포인터 이동, 입력으로 돌아오는 구간을 나눴다. 해당 연구의 homing time에는 반응 시간도 포함된다. 또 25명 중 14명이 전환용 Tab 키를 좋아하지 않았고 일상적인 Tab 의미와의 혼동을 논의했다. 손 왕복이 짧다는 사실만으로 전환 규칙도 편하다고 가정하지 않을 근거다. 최종 장비는 IR 표식·Wii Remote와 키보드 버튼을 사용했으므로 RGB 웹캠 결과로 일반화하지 않는다. [저자 원문](https://www.julian-ramos.com/papers/Ramos2016.pdf)

### 전환 방식을 먼저 분리

| 비교 후보 | 언제 제어를 쉬는가 | 다시 포인팅할 때 | 먼저 확인할 비용·한계 |
| --- | --- | --- | --- |
| 현재 공통 절차: 휴식 구역 확인 | 작업 종료 뒤 사용자가 휴식 구역으로 손을 옮겨 대기 | 유효 추적·새 시작 요청·새 위치 기준 | 키보드까지 가기 전 우회 동작, 쉬기/시작을 잊음, 클릭 후보 중 휴식의 의미 |
| 키보드 근처 구역 진입 | 기존 작업을 정상 종료한 뒤, 카메라가 구별할 수 있는 키보드 측 구역 도착을 대기 진입 사건으로 사용 | 같은 명시적 새 시작 절차 | 손을 옮기는 도중의 커서 이동, 조작 구역과 겹침, 키보드·손 가림과 경계 인식 |
| 키 입력을 이용한 보조 중단 | 회차에서 정한 키 활동을 제어 중단 신호로 사용하는 후보. 지속 작업의 처리는 아래에서 분리 | 입력이 잠시 없다는 이유로 자동 재개하지 않고 새 시작 | 첫 키 전에 이미 생긴 이동/hover를 되돌리지 못함. modifier·단축키·조합 입력·지속 작업 정책 필요 |

먼저 현재 공통 절차에서 실제로 어느 왕복이 막히는지 본다. 부담이 크면 키보드 구역 후보와 같은 손 수·클릭 문법으로 비교한다. 키 입력 보조는 모든 키를 타이핑으로 취급하는 안으로 넣지 않는다. 세 방식·한 손/두 손·자세를 한 번에 전부 교차하지 않는다. 위 대안은 R0에 추가된 기능이나 선택된 제품 정책이 아니다.

### 정상 입력과 제어 중단을 구별할 경계

- **필드 선택 후 입력:** 정상 클릭을 완료한 뒤 쉬기·타이핑·새 제어 진입의 비용을 기록한다. 쉬기를 생략하고 바로 키보드로 가는 장면도 반증 과제로 남긴다. 운영자가 손의 목적을 보고 대기 카드를 미리 넣어 주지 않는다.
- **포커스:** 쉬기·재진입의 상태 표시가 대상 앱의 키보드 포커스를 가로채지 않아야 한다. 실제 키가 엉뚱한 창으로 갔다면 제어가 쉬었다는 사실만으로 전환 성공으로 세지 않는다. 조용한 포커스 복원·문자 재전송으로 결과를 보정하지 않는다.
- **Ctrl/Shift 병행:** 물리 키를 누른 채 웹캠으로 클릭·드래그하는 경우는 글자 입력과 구분한다. 키 입력마다 무조건 대기하면 이 작업이 깨질 수 있다. Windows 마우스 메시지도 Ctrl·Shift 상태를 함께 표현한다. 앱별 최종 선택·복사/이동 결과를 확인한다. [WM_LBUTTONDOWN 공식 문서](https://learn.microsoft.com/en-us/windows/win32/inputdev/wm-lbuttondown)
- **남은 지속 작업:** 기본 비교 절차는 스크롤·드래그를 기존 규칙으로 끝낸 뒤 타이핑한다. 종료를 놓친 상태에서 입력하는 장면은 별도 실패 과제다. 키 입력으로 자동 해제한다면 드롭·선택 확정 가능성이 있고, 눌림을 유지한 채 멈춘다면 눌린 상태로 입력이 계속되는 문제가 있다. 이 선택을 정하기 전 키 입력 보조가 지속 작업까지 해결한다고 설명하지 않는다.
- **후보 중 키 입력:** 아직 OS에 보내지 않은 요청과 키 활동의 경합은 선택한 전환 방식에서 정한다. 키 입력 보조 후보라면 중단 대상 키가 확인된 뒤 남은 요청을 폐기하는 안을 검토하되, 이미 보낸 클릭은 되돌릴 수 없다. 과거 카메라 프레임의 늦은 결과가 중단 뒤에 실행되지 않도록 관찰 순서도 확인한다.
- **한글 입력:** 첫 키 누름, 화면의 조합 중 문자, 확정된 문장은 다른 관찰이다. 조합 중 클릭·쉬기·다른 목표 선택이 문자와 포커스에 어떤 결과를 만드는지 실제 앱에서 확인한다. 키 하나를 입력 성공 한 글자로 세지 않는다. [Windows IME 조합 모델](https://learn.microsoft.com/en-us/windows/win32/intl/wm-ime-composition)

### 두 손 후보에서 남길 제약

C1/C2의 명령 손이 키보드에 있고 공간 손만 유효하게 보이면, 손이 안 보이는 경우와 달리 **명령 손의 타이핑이 제스처로 오인될 수 있다**. 키보드 영역의 손에서 명령을 받지 않는 안은 오실행을 줄일 수 있지만, 그 손으로 Ctrl/Shift를 누른 채 클릭·드롭을 요청할 수 있는지도 함께 따져야 한다.

같은 손이 modifier를 누르면서 정해진 명령 동작을 편하게 할 수 있는지 확인하지 않고 가능하다고 가정하지 않는다. 명령을 공간 손에 자동 이전하거나 두 손 후보에만 modifier 토글 기능을 추가해 비용을 없앤 것으로 처리하지 않는다. 그런 대안이 필요하면 추가 규칙과 학습 비용을 가진 별도 후보로 표시한다. C1/C2의 기존 종료·손실 문법은 유지하며, 일반 모양 미판정과 키보드 구역 진입을 같은 사건으로 합치지 않는다.

따라서 한 손/두 손 비교에는 순차 타이핑 왕복뿐 아니라 물리 modifier 병행의 완결성을 포함한다. 다른 손이 키보드에 있는 동안 포인터만 움직일 수 있다는 사실은 클릭·드롭까지 가능하다는 증거가 아니다.

### 전체 왕복을 측정할 기준

아래는 후속 실제 센서 평가의 기록 설계다. 사람 모사 단계에서는 이해·혼동·예상·불편만 관찰하며 진행자의 반응 속도를 제품 성능으로 쓰지 않는다.

| 시점 | 정의 |
| --- | --- |
| 과제 단서 | 다음 목표를 알린 시각. 반응 시간의 시작이며 손이 이미 준비됐는지도 기록 |
| 손 이동 시작/키보드 도착 | 영상으로 구별 가능한 물리 경계. 관찰이 안 되면 추정값 대신 결측과 이유 |
| 제어 시작 요청/수락 | 새 요청의 시작과 제어 진입 수락을 분리. 물리 마우스 M에는 해당 없음 |
| 첫 의도한 포인터 입력 | 목표를 위한 첫 이동 또는 버튼 입력. 커서가 이미 목표 위라 움직임 없이 클릭한 경우도 구분 |
| 클릭 전달/실제 목표 완료 | OS 클릭과 올바른 항목·포커스 결과를 별도 기록 |
| 첫 키/첫 올바른 표시 | 실제 키 입력과 올바른 필드의 최초 입력 표시를 분리. 조합 중인지도 기록 |
| 입력 과제 완료 | 지정 문장이 의도한 필드에 확정된 상태. 수정·포기·잘못된 창 입력도 보존 |

과제 단서→실제 목표 완료, 클릭 전달→첫 올바른 입력 표시, 왕복 전체 완료를 함께 보고한다. 반응·손 이동·새 시작이 섞인 구간을 ‘순수한 손 이동 시간’으로 부르지 않는다. 두 손 동작과 타이핑이 겹친다면 시점을 그대로 남기며 겹치는 구간을 더해 전체 시간보다 긴 분해 합계를 만들지 않는다. 수동 영상·OS·앱 로그의 시계가 맞지 않으면 그 해상도보다 정밀한 시간 차이를 주장하지 않는다.

## 긴 이동과 손 재배치

편한 손의 이동 범위가 작으면 넓은 화면을 이동하거나 긴 드래그를 이어갈 경로가 필요하다. 손을 편한 위치로 되돌리는 재배치는 물리 마우스를 잠깐 들어 옮기는 것과 비슷한 역할을 하지만, 웹캠에서는 버튼 눌림과 위치 출력을 따로 다뤄야 한다. 손을 시야 밖으로 빼는 것만으로 의도한 재배치를 추정하면 추적 손실과 구분할 수 없다.

재배치 횟수만 줄이는 것을 목표로 삼지는 않는다. 노트북 트랙패드의 한 통제 실험은 재배치를 허용하지 않은 움직임이 더 어렵고 오류·준비 시간이 늘었으며 더 빠르지도 않았다고 보고했다. 가정용 웹캠의 결과는 아니지만 ‘재배치 없는 조작이 언제나 더 낫다’는 전제를 피할 근거다. [저자의 연구 요약: Clutching Is Not (Necessarily) the Enemy, CHI 2015](https://mathieu.nancel.net/)

### 다음 회차에서 비교할 범위

다음은 **한 손 B2의 드래그를 확장하기 위한 후보**다. R0의 고정 조건에 조용히 추가하지 않는다. 손 수·클릭·메뉴 진입·자세를 함께 바꾸지 않고 비교한다.

| 후보 | 구체적인 작업 흐름 | 먼저 드러낼 실패 |
| --- | --- | --- |
| 별도 짧은 요청으로 재배치 | 드래그 중 새 재배치 요청 → 커서 고정·button-down 유지 → 손을 편한 위치로 → 새 재개 요청 → 새 기준으로 드래그 계속 | 드롭용 pinch와 충돌, 재개를 잊음, 구별할 추가 동작의 부담 |
| 관찰되는 공간 구역으로 재배치 | 조작 구역에서 별도 재배치 구역 진입 확인 → 커서 고정·button-down 유지 → 편한 복귀 위치의 별도 재개 구역 도착 확인 → 새 기준으로 계속 | 경계까지 이동하며 커서가 달라짐, 우발 경계 진입, 재개 위치 찾기, 휴식 구역과 혼동, 좁은 웹캠 시야 |
| 위치에 따라 이동 속도를 주는 방식 | 중립 위치에서 벗어난 정도로 커서 속도 결정 → 중립으로 돌아와 멈춤 | 손을 멈춰도 커서가 계속 가는 의미, 정밀 목표·멈추기·중립 유지 부담 |
| 편한 손 영역 전체를 화면에 대응 | 손의 작업 영역을 화면 전체에 대응시키는 절대 매핑 | 작은 목표의 정밀도, 지지 자세 변화·손 깊이 변화, 가림 후 좌표 대응의 이해 |

첫 비교에서는 위의 **두 재배치 후보**만 좁혀 살핀다. 속도 제어나 절대 매핑은 재배치 후보로 작업을 완결하기 어려울 때 다음 대안으로 남긴다. 속도 제어를 고르면 손의 정지와 커서 정지가 일치하는 기존 문법을 승계하지 않는다. 절대 매핑을 고르면 상대 이동의 새 기준점 규칙과 같은 조건으로 취급하지 않는다.

감도·속도에 따른 증폭을 바꾸는 방법은 각 후보와 별도 요인이다. 큰 감도는 같은 손 범위로 먼 목표에 닿게 하지만 작은 목표의 흔들림도 키울 수 있다. RubberEdge는 위치·속도 제어를 결합하면서 전환과 탄성 피드백을 다뤘다. 특수 장치의 이점을 촉각 경계가 없는 RGB 맨손 조작에서도 얻는다고 가정하지 않는다. [RubberEdge 원문, UIST 2007](https://arxiv.org/pdf/0804.0556)

### 두 재배치 후보가 공유할 계약

- 정상 재배치에서 button-up을 보내지 않는다. `드래그: down 유지 → 재배치: down 유지·커서 고정 → 재개: down 유지·새 기준 → 정상 드롭: up`을 구분한다.
- 재배치 중에도 같은 손의 새로운 위치와 신원이 유효해야 한다. 관찰이 끊기면 공통 소실 해제로 넘어가며 드롭 가능성이 있다. 보이지 않는 동안 눌림을 유지하는 능력으로 설명하지 않는다.
- 휴식·소실·중지는 재배치가 아니다. 휴식 구역과 재배치 구역을 같은 상태의 같은 관찰로 동시에 약속하지 않는다. 구역을 구분할 수 있는 시야가 없으면 공간 후보의 가정이 실패한 것이다.
- 종료용 요청, 재배치 요청, 재개 요청은 그때의 상태에서 충돌하지 않아야 한다. 같은 신호를 다른 상태에서 재사용할 수는 있지만 진입 요청의 잔여 동작이 즉시 재개·드롭이 되지 않도록 소비한다.
- 재배치 진입은 진행 중인 다른 요청이 없을 때만 받는다. 드롭 후보가 이미 시작됐다면 재배치 요청이나 재배치 구역 진입을 실행·예약하지 않고 기존 후보를 완료/취소/만료 규칙으로 처리한다. 예를 들어 `드롭 후보 닫힘 → 재배치 구역 → 정상 열림`은 재배치 성공이 아니라 현재 보이는 위치의 드롭이다. 사용자가 재배치를 의도했다는 이유로 이미 진행 중인 종료 요청을 바꿔 해석하지 않는다.
- 공간형은 조작 구역 경계에 돌아왔다는 사실만으로 재개하지 않는다. 편한 복귀 위치에 재개 구역을 정하고, 그곳에 도착한 새 관찰을 확인할 때까지 커서를 고정한다. 재배치 진입 구역과 재개 구역이 겹쳐 즉시 왕복 전환하지 않도록 한다. 실제로 구역들을 볼 수 있는지와 재개 위치를 찾아야 하는 부담은 후속 검증 대상이다.
- 재배치 중 메뉴·설정으로 입력 소유권을 넘기지 않는다. 현재 작업을 먼저 정상 종료하거나 공통 중지를 사용하며, 나중에 새 요청을 받는다.

### 같은 긴 드래그의 동작 분해

아래는 실제 수행 자료가 아닌 **조작 규칙의 명목상 단계 수**다. 비교의 시작은 이미 제어가 켜진 이동 상태이며 B2의 메뉴 열기 → 드래그 선택 → 잡기 → 드롭을 사용한다. 각 요청은 새로운 시작부터 완료까지의 한 주기다. 손가락을 붙이고 떼는 두 위상을 요청 두 번으로 세지 않는다. 최초 앱 실행·제어 진입은 별도 공통 비용이며, 매 드래그에 다시 필요하다고 가정하지 않는다.

| 진입→재개까지 완료한 재배치 후 드롭 | 짧은 요청형의 완료된 요청 주기 | 공간형의 완료된 요청 주기 | 공간형의 추가 구역 사건 | 두 방식 공통의 재배치 상태 전환 |
| --- | --- | --- | --- | --- |
| 없음 | 4 | 4 | 0 | 0 |
| 한 번 | 6 | 4 | 진입 1 + 재개 도착 1 | 진입·복귀 2회 |
| 두 번 | 8 | 4 | 진입 2 + 재개 도착 2 | 진입·복귀 4회 |

기본 4주기는 메뉴 열기·도구 선택·잡기·드롭이다. **진입→재개까지 완료하고 드래그를 이어간 재배치 n번**에 짧은 요청형은 `2n`주기가 추가된다. 공간형은 추가 손모양 주기가 없어도 `2n`개의 구역 확인과 그곳까지의 손 이동이 필요하다. 양쪽 모두 손을 편한 위치로 되돌리는 물리 경로가 남는다. 구역 진입 전의 커서 이동, 구역 찾기, 잘못된 요청과 경계의 재시도는 이 표에 없는 실제 비용으로 추가 기록한다.

재배치에 들어간 뒤 재개 없이 그 자리에서 드롭하는 정상 종료는 별도 경로다. `메뉴 → 드래그 선택 → 잡기 → 재배치 진입 → 재개 없이 드롭`은 짧은 요청형 5주기, 공간형 4주기와 구역 진입 1개다. 종료하려는 사용자에게 표의 횟수를 맞추기 위해 재개를 추가시키지 않는다.

이 수를 초 단위 시간·피로·오류율로 환산하지 않는다. 실제 짧은 재배치 요청의 모양도 아직 선정하지 않았으므로 짧다는 이름만으로 수행이 쉽다고 가정할 수 없다. 다른 상태에서 기존 신호를 재사용하면 외울 모양은 줄 수 있으나 상태에 따라 뜻을 구분해야 하는 비용이 생긴다. 공간형의 요청 주기 수만 보고 더 빠르다고 선택하지 않는다.

드래그 도구에 직접 요청으로 들어가는 별도 조건은 기본 주기가 3이며 전체 표가 달라진다. 메뉴형과 직접 요청형을 한 조건의 시도 안에서 섞지 않는다. B1의 한 번 붙여 유지했다 떼는 드래그와도 유지 시간·도구 진입이 달라, 이 요청 수를 후보 전체의 순위로 사용하지 않는다.

### 재배치 도중 종료와 거부된 사건의 재준비

두 재배치 후보에 다음 규칙을 제안한다. 재배치를 시작한 뒤에도 **새 정상 드롭 요청은 받을 수 있다**. 끝내기 위해 손을 먼저 움직이는 상태로 복귀하도록 강요하지 않는다. 단, 재배치 중에는 커서 위치만 고정되고 button-down이 남아 있다는 사실을 계속 표시한다.

| 현재 상태와 새 관찰 | 제안한 처리 | 후속 요구 |
| --- | --- | --- |
| 재배치 중 새 드롭 후보 → 정상 열림 | 고정된 보이는 위치에서 up 한 번, 이동으로 전환 | 현재 손 위치로 새 기준. 추가 클릭 없음 |
| 재배치 중 새 드롭 후보 → 후보만 취소/만료 | up 없음, **재배치 유지**, 커서 고정 | 잔여 열림 소비. 새 종료 또는 새 재개 필요 |
| 재배치 중 새 드롭 후보와 재개가 경합 | 드롭 요청 처리를 우선하고 재개는 실행·예약하지 않음 | 드롭이 만료돼도 거부된 재개를 뒤늦게 실행하지 않음 |
| 드래그에서 드롭 후보 중 공간 재배치 구역 진입 → 후보 만료 | 재배치 진입을 뒤늦게 실행하지 않음. 드래그 유지 | 구역 이탈 후 새 진입 필요. 이탈 중 커서 이동도 기록 |
| 재배치에서 드롭 후보 중 재개 구역 도착 → 후보 만료 | 재개하지 않고 재배치 유지 | 재개 구역 이탈 후 새 도착 또는 허용된 새 종료 요청 |
| 재배치 요청이 끝났지만 손이 같은 요청 모양에 머무름 | 같은 수행으로 바로 재개하지 않음 | 다음 독립 요청의 시작을 확인 |
| 공간형에서 재개한 뒤 다시 범위 끝에 도달 | 다음 새 진입·도착을 각각 확인 | 이전 구역 확인을 재사용하지 않음 |
| 범위 끝에서 새 요청·구역 이탈·재진입을 관찰 가능하게 수행할 수 없음 | 정상 재배치 성공으로 처리하지 않음 | 미완료·복구를 기록. 공통 중지의 해제·드롭 가능성 유지 |
| 재배치 중 타이핑을 하려고 휴식 / 소실 / 중지 | up 후 각각 대기 / 보류 / 중지 | 기존 드래그 자동 복원 없음. 실제 선택·드롭 결과를 별도로 기록 |

여기서 ‘후보만 취소’는 제어 세션의 휴식·중지와 다르다. 휴식·소실·중지는 공통 해제 규칙을 따른다. R0의 드래그 종료 후보 만료는 원래 드래그 상태로 돌아갔지만, 재배치 안에서 만든 종료 후보는 원래 **재배치**로 돌아간다. 이 차이를 임의로 생략하면 의도하지 않은 커서 재개가 생긴다.

### 커서 고정과 대상 앱의 변화

드래그 중 커서가 창 가장자리에 있으면 대상 앱이 내용을 자동으로 스크롤할 수 있다. 예를 들어 Qt의 QAbstractItemView는 조건에 맞는 가장자리 드래그에서 뷰 자동 스크롤을 제공한다. 이 사실이 모든 Windows 앱의 동작을 보장하지는 않는다. [Qt 공식 문서의 autoScroll](https://doc.qt.io/qt-6.10/qabstractitemview.html#autoScroll-prop)

따라서 재배치가 OS 커서 이동과 자체 스크롤 출력만 멈춘다는 사실에서 **문서 내용·선택 범위·드롭 대상까지 정지한다**고 추론하지 않는다. ForceEdge 연구도 긴 선택과 물체 이동 중 자동 스크롤을 별도 제어 문제로 다뤘다. 해당 연구는 힘 감지 장치를 사용했으므로 그 입력법을 RGB 웹캠 기능으로 간주하지 않는다. [ForceEdge 원문, CHI 2017](https://gery.casiez.net/IHMA/TP_R/3025453.3025605.pdf)

첫 문법 비교는 자동 스크롤이 없는 고정 화면 구간으로 한정해 두 재배치 방법을 살핀다. 이어 별도 장면에서 가장자리 자동 스크롤이 발생하는 긴 문장 선택·목록 이동을 두 후보에 동일하게 포함한다. 진행자가 재배치 카드 동안 내용을 임의로 멈춰 주지 않는다. 실제 앱 평가에서는 재배치 중 내용 이동, 의도한 선택 끝점·드롭 대상 변화, 복구 비용을 기록한다. 앞선 고정 화면 과제의 성공만으로 일반 앱의 긴 선택을 통과시키지 않는다.

### 검토 과제와 판정

먼 목표 이동, 작업 범위를 넘는 드래그, 긴 문장 선택, 창 이동을 같은 자세·감도에서 따라간다. 목적 앱이 지원하는 가장자리 자동 스크롤이 필요하면 그 동작을 별도로 기록한다. 손 범위의 재배치와 앱의 자동 스크롤을 같은 기능으로 세지 않는다.

완료까지의 전체 동작 수·재배치 횟수·고정/재개 혼동·원치 않은 드롭·복구 시간·손가락과 팔 부담을 함께 남긴다. 짧은 요청형은 별도 동작을 만들 수 있는지, 공간형은 경계와 휴식 영역을 카메라가 함께 볼 수 있는지가 우선 질문이다. 문서나 몸동작만으로 인식률·초 단위 지연·장시간 부담을 통과시킬 수 없다. 현재 두 후보 모두 사용자·센서 검증 전이다.

버튼을 누르지 않은 일반 포인터 재배치는 드래그와 분리한다. 기본 `쉬기 → 새 진입·새 기준` 경로를 먼저 기준으로 두고, 별도 재배치가 그 복귀 비용을 줄이는지 비교한다. 위 표의 button-down 계약과 주기 수를 일반 이동에 그대로 적용하지 않는다.
