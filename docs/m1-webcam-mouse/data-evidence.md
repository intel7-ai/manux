# M1 상호작용을 검증할 데이터의 범위

공개 데이터는 손 위치 추정과 모양 구분에 도움을 줄 수 있다. M1의 사용자 의도·클릭 경계·드래그 종료·휴식·타이핑 복귀는 제품의 상호작용 규칙이 정해져야 평가할 수 있다. 데이터의 전체 용량과 이 규칙의 검증 범위를 구분한다.

## 공개 자료를 사용할 질문

| 자료 | 제공하는 근거 | M1에서 검토할 용도 | 별도 검증할 항목 |
| --- | --- | --- | --- |
| [HaGRIDv2 공식 자료](https://github.com/hukenovs/hagrid/blob/master/README.md) | 다양한 RGB 이미지의 손 검출·모양 클래스, 자연 손모양 `no_gesture` 일부 | 기본 요청 신호 후보 구분과 배경·조명 변화 | 클릭 한 번의 시간 경계, 중도 포기, 긴 비명령 구간, 포인터 흔들림 |
| [NVGesture 공식 연구](https://research.nvidia.com/publication/2016-06_online-detection-and-classification-dynamic-hand-gestures-recurrent-3d) | 연속적인 다중 센서 입력에서 동작 검출·분류 | 시작·핵심 동작·복귀를 분리하는 시간적 평가 | 운전 맥락의 오른손 동작을 책상·키보드·양손 제어로 옮기는 차이 |
| [FreiHAND 공식 프로젝트](https://lmb.informatik.uni-freiburg.de/projects/freihand/) | RGB에서 3D 손 관절과 형태 추정, 다른 데이터로의 일반화 문제 | 위치 추정과 관절 오차의 평가 방식 | 한 장의 포즈 오차와 연속 커서 안정성의 차이, 실행 의도 |
| [InterHand2.6M 공식 프로젝트](https://mks0601.github.io/InterHand2.6M/) | 한 손·겹치는 두 손의 3D 관절, 시간 연구용 30fps 버전 | 양손 가림·상대 위치·순서 있는 영상의 추적 평가 | 어느 손이 명령 손인지, 키보드 복귀, 의도 없는 활성화 |

HaGRIDv2의 공식 표기는 전체 이미지 규모 **1.5T**, FullHD RGB 이미지 **1,086,158장**이다. 이것은 “튜닝된 부분의 용량”을 뜻하지 않는다. 또한 공식은 정적인 모양으로 학습하고 시간·순서·위치 관계를 이용하는 동적 인식 알고리즘을 별도로 제공한다. 따라서 정적 이미지가 동적 제어에 전혀 도움이 되지 않는다고 단정할 수도 없다. [공식 README](https://raw.githubusercontent.com/hukenovs/hagrid/master/README.md)

위 수치는 공식 제공 범위이며 이 프로젝트가 실제로 확보·검증한 데이터 용량의 기록이 아니다. 이번 설계 검토에서는 데이터셋을 다운로드하거나 모델을 학습하지 않는다.

NVGesture의 RGB·깊이·IR 결과를 RGB만 사용하는 앱에 그대로 적용하지 않는다. InterHand2.6M의 여러 카메라에서 같은 순간을 본 영상 수를 독립된 사용자 행동 수로 세지 않는다. 데이터셋 자체의 검증 성적과 실제 가정 환경의 일반화 성능도 구분한다.

## 컨셉 결정 후 직접 기록할 연속 행동

| 행동 구간 | 성공 사례와 함께 남길 실패 | 확인할 질문 |
| --- | --- | --- |
| 편한 손의 포인터 이동 | 손 위치는 유지하며 손가락만 바꾸기, 작은 이동·정지·긴 이동 | 모양 변화가 위치 제어에 섞이는가? |
| 클릭 전체 과정 | 붙이기·떼기·길게 유지·중도 포기·의도한 두 번 클릭 | 한 요청이 몇 번 실행되고 언제 확정되는가? |
| 드래그·스크롤 | 시작·정상 종료·잘못된 종료·소실·복귀 | 눌림이나 도구 상태가 남는가? 예상 밖 드롭이 있는가? |
| 비명령 행동 | 타이핑·컵 들기·얼굴 만지기·대화 손짓·읽기 | 요청하지 않을 때 얼마나 자주 명령이 발생하는가? |
| 손 소유권과 복귀 | 양손 교차·가림·다른 손 진입·손 재등장 | 역할이 바뀌거나 이전 명령이 다시 실행되는가? |
| 실제 작업 흐름 | 작은 목표·문장 선택·긴 스크롤·키보드와 왕복 | 인식 성공이 작업 완료로 이어지는가? |

성공 동작만 잘라낸 클립은 긴 비명령 구간의 시간당 오실행을 평가하지 못한다. 시작 전과 종료 후를 포함한 연속 관찰 시간을 남기고, 실패·재시도·휴식도 보존한다. 원시 영상은 필요한 경우에만 수집하며, 참가자에게 목적과 보존 범위를 설명한 뒤 동의를 받는 절차를 준비한다.

## 주석과 평가 단위

| 항목 | 기록 방법 |
| --- | --- |
| 의도 | 지시한 과제와 참가자가 확인한 의도; 영상만 보고 마음속 의도를 정답으로 단정하지 않음 |
| 관찰 | 손동작 시작·핵심 변화·끝, 가림·소실·재진입 시각 |
| 시스템 | 추적 품질, 수락·거절된 요청, 현재 상태, OS로 보낸 사건 |
| 결과 | 목표 적중, 작업 완료, 중간 수정, 예상 밖 드롭, 도움·물리 마우스 복귀 |
| 맥락 | 참가자·세션·카메라·조명·거리·주손·팔 지지 |
| 불확실성 | 의도나 사건 경계가 모호하면 불확실로 남기고 억지로 확정하지 않음 |

학습과 평가를 나눌 때 사람·세션·장치의 분리를 우선한다. 원본 연속 녹화와 그 잘라낸 클립·재인코딩·증강본을 같은 원본 녹화 ID에 묶고 모두 같은 분할에 둔다. 같은 행동의 인접 프레임이나 가공본을 학습·평가 양쪽에 섞지 않는다.

명령 성공은 독립 행동 시도 단위로 보고한다. 비명령 오실행은 활성·대기·중지 상태별 관찰 시간과 사건 수를 나누고, 의도 없는 세션 진입과 의도 없는 OS 명령을 별도 기록한다. 중지 시간을 길게 넣어 활성 상태의 오실행률을 낮추지 않는다. 사람별 분모와 실패 조건을 유지한다.

한 세션의 관찰 시간을 사건 행마다 반복해 더하지 않는다. 의도가 불확실한 구간은 확실한 비명령 시간과 구분하고, 모호한 시간과 사유를 별도로 기록한다. 동기화된 시스템 사건이나 화면 기록이 없으면 해당 항목을 미측정으로 남긴다.

손을 멈췄을 때의 커서 흔들림은 인체 떨림과 센서·필터의 영향을 함께 포함하는 제품 지표다. 외부 위치 정답 없이 이를 3D 관절 추정 오차라고 부르지 않는다. 추론 시간, 요청 확정 대기, 화면 반응 지연, 전체 과제 시간도 각각 다른 값으로 기록한다.

이 규약을 먼저 정한 뒤 필요한 실패 조건을 보강한다. 수집 용량을 늘린 사실이 사용자의 지속 자세 부담이나 모드 이해 문제를 해결했다는 근거를 대신하지는 않는다.

## 직접 버튼 대응의 연속 평가

G0 같은 누름/해제 대응 후보에는 사진 한 장의 모양 정답뿐 아니라 **버튼 사건과 유지 구간**의 정답이 필요하다. 아래는 후속 평가 규약 제안이며 데이터를 이미 수집·채점한 결과가 아니다.

| 기록 | 평가할 차이 |
| --- | --- |
| 의도한 누름·해제 시도와 관찰 가능한 시작/끝 | 사용자 과제·확인 의도와 영상의 시간 경계. 실제 손가락 접촉·힘의 정답으로 부르지 않음 |
| 수락한 down/up과 대상 손·상태 | 의도 사건과 실제 사건을 일대일로 대응. 여분·누락 사건을 성공 프레임으로 덮지 않음 |
| 원치 않은 down | 비명령 노출 시간별 사건 수. 오래 중지한 시간을 더해 낮추지 않음 |
| 유지 중 원치 않은 up | 원한 누름이 끊긴 시도 수·위치·앱 결과. 뒤에 다시 down이 생겨도 실패를 지우지 않음 |
| 종료 시도 뒤 down 잔류 | 실제 up 또는 공통 중지까지의 잔류 시간, 미해제·미완료와 복구. up이 없으면 지연 0으로 대체하지 않음 |
| 정상 전이·관찰불가·후보 마감 | 다른 원인을 구분한 해제 수와 시간, 보류·재진입 비용 |
| 실제 앱 결과 | 클릭·드롭·선택·누름 동안의 반복 동작을 OS 버튼 사건 수와 별도 기록 |

완전한 한 주기의 성공은 올바른 down과 up이 각각 한 번, 필요한 유지가 끊기지 않음, 목표 앱의 작업 결과까지 함께 본다. ‘누름 상태인 프레임의 비율’만 높이는 지표는 끝내지 못한 버튼을 좋은 결과로 만들 수 있다. 반복 오실행은 원시 사건 수와 연속 실패 구간을 모두 남긴다. 앱 자체의 누름 반복 기능과 주입한 down의 중복도 구분한다.

촬영된 프레임, 처리된 프레임과 그 입력 시각, 추론 완료, 요청 수락, OS 전달, 화면 결과의 시각을 구분한다. 처리되지 않은 구간에 짧은 닫힘이 있었다고 결과를 만들어 보충하지 않는다. 관찰 가능한 시간 경계가 범위로만 주어지면 그 불확실성과 사건 대응 허용 범위를 사전에 기록한다. 사람이 의도한 클릭을 했다고 확인했어도 영상에서 경계가 안 보이면 의도 시도 수와 경계 미측정을 따로 남긴다.

MediaPipe Python의 live stream 문서는 처리 중 새 입력 프레임이 무시될 수 있고 입력 프레임 시각을 제공해야 한다고 설명한다. 이는 해당 API의 동작이며 현재 웹 앱에서 같은 버그가 발생했다는 진단이 아니다. SDK·실행 경로가 달라질 때도 카메라 명목 FPS와 실제 처리 관찰 밀도를 같은 값으로 가정하지 않을 근거다. [공식 가이드](https://developers.google.com/edge/mediapipe/solutions/vision/hand_landmarker/python)

확인 규칙을 ‘연속 몇 프레임’만으로 정하면 실제 관찰 간격이 달라질 때 기다림도 달라진다. 후속 회차에서는 확인 기간·필요한 새 관찰·허용 공백을 함께 명시하고 실제 간격을 보고한다. 관찰이 없는 긴 공백을 단순히 유지 시간으로 채우지 않는다. 추론 시간만으로 실제 손동작부터 앱 결과까지의 지연을 대표하지 않는다.
