# 클릭 요청의 시작 완료 포기와 재준비

커서 추적을 손모양 유지에서 분리해도 클릭 한 번의 경계는 별도로 설계해야 한다. 이 문서는 [조작 시나리오](candidate-storyboards.md)의 빈칸을 확인한 설계 검토안이다. 제품 동작·제스처 시간값·사용자 시험 결과가 아니다.

## 같은 관찰로 다른 의도를 구분할 수 없는 경우

다음 두 사용자는 영상에서 똑같이 `손가락을 붙임 → 잠깐 유지 → 뗌`을 보일 수 있다.

- 첫 번째 사용자는 처음부터 끝까지 클릭하려고 했다.
- 두 번째 사용자는 클릭하려고 붙였지만 마음을 바꿔 손을 풀었다.

다른 관찰이나 신호가 없다면 두 의도를 구분할 근거가 없다. 두 번째 사례를 인식 정확도 문제로만 취급하지 않는다. “떼면 클릭”을 약속했다면 평범하게 떼는 행위를 동시에 취소로 약속할 수 없다. 취소 신호·후보 만료·확정 시점 중 무엇을 쓸지 사용자 규칙으로 정해야 한다.

## 비교할 두 클릭 규칙

여기서 닫힘과 열림은 해당 클릭 신호의 시작·해제를 뜻한다. 손가락 전체를 펴는 특정 중립 자세를 뜻하지 않는다. pinch는 설명을 위한 예시이며 기본 제스처로 확정하지 않는다.

| 규칙 | 확정 전 | 확정 순간 | 이후 | 주요 비용 |
| --- | --- | --- | --- | --- |
| G1 닫힘 확정 때 실행 | 닫힘 후보를 확인하는 동안 OS 클릭 없음 | 닫힘이 확정되면 클릭 한 쌍 | 계속 닫아도 반복 없음. 새 열림을 확인한 뒤 다음 새 닫힘 허용 | 반응이 빠를 수 있으나 닫힘 확정 뒤의 포기는 이미 늦음 |
| G2 열림 확정 때 실행 | 닫힘은 아직 클릭하지 않은 후보 | 취소·만료·다른 작업 전환 없이 열림이 확정되면 클릭 한 쌍 | 같은 열림으로 재실행 없음. 이후의 새 닫힘이 다음 시도 | 클릭 완료까지 한 동작 주기를 기다림. 포기 규칙이 별도로 필요 |

어느 규칙도 클릭을 받은 앱의 작업을 일반적으로 되돌려 주지 않는다. G1의 확정 뒤 손을 떼는 것은 클릭 취소가 아니라 다음 시도를 준비하는 동작이다. G2에서 후보가 아직 유효하다면 평범하게 떼는 것은 클릭 완료다.

## B1과 B2에 함께 적용하면 생기는 차이

B1은 같은 닫힘을 클릭 후보로 두었다가 움직이면 드래그로 전환하는 후보이다. 이 닫힘에 G1의 완성된 클릭을 이미 보냈다면, 나중에 드래그라는 사실을 알아도 앞선 클릭을 없앨 수 없다.

| 조합 | 검토 결과 |
| --- | --- |
| B1의 같은 닫힘으로 클릭·드래그 판별 + G1 즉시 클릭 한 쌍 | 그대로는 양립하지 않음. 드래그 전에 선행 클릭이 발생함 |
| B1 + G2 후보 판별 | 클릭을 보내기 전에 드래그로 넘길 여지가 있음. 전환 뒤 열림은 버튼 해제만 하고 클릭 후보는 폐기해야 함 |
| B2의 별도 드래그 도구 준비 + G1 | 일반 클릭과 도구의 잡기·드롭을 상태별로 구분할 수 있으나, G1이 더 편하거나 정확하다는 증거는 아님 |
| B2 + G2 | B1과 같은 클릭 규칙을 유지하며 드래그의 유지/단계 차이를 비교할 수 있음 |

B1/B2를 비교할 때 클릭 규칙까지 바꾸면 두 요인의 효과가 섞인다. 초기 리허설은 같은 G2 규칙으로 맞추는 안을 우선 검토하고, G1은 별도 도구 준비가 있는 문법에서 후속 비교한다. 이것은 실험을 구성하기 위한 제안이며 G2를 제품 기본값으로 선정한 결과가 아니다.

## 추가 선행 후보 G0: OS 누름·해제를 직접 대응

앞선 G1/G2는 **완성된 클릭 down/up 한 쌍을 언제 보낼지**에 관한 두 규칙이다. 모든 가능한 마우스 입력 문법을 뜻하지 않는다. 추가 검토할 G0는 `새 닫힘 확인 → down 한 번`, `닫힘 유지 중 새 위치 → 이동`, `유효한 열림 → up 한 번`으로 대응한다. 일반 포인터 이동에는 특정 명령 모양의 계속된 유지를 요구하지 않는다. 집기 예시는 바꿀 수 있으며 G0도 제품 기본값이나 구현된 기능이 아니다.

Win32의 공식 예시는 down에서 시작 위치·입력 캡처를 정하고, 눌림 중 이동을 처리하다 up에서 마치는 흐름을 보여 준다. 따라서 대상 앱이 down·이동·up을 해석하도록 하는 경로도 비교할 가치가 있다. 이것은 일반 RGB 웹캠의 성공률 근거가 아니다. [Using Mouse Input](https://learn.microsoft.com/en-us/windows/win32/inputdev/using-mouse-input)

| 구분 | G0 직접 누름/해제 | 기존 B1의 G2+이동 판별 | B2 R0 |
| --- | --- | --- | --- |
| OS에 down을 보내는 때 | 유효한 새 닫힘 | 드래그 이동 인계 때. 일반 클릭은 열림 때 pair | 별도 도구 준비 뒤 잡기 주기 완료 |
| 클릭/드래그의 해석 | 앱이 down 이후 경로·해제를 처리 | 제어 계층이 먼저 클릭 후보/드래그를 판별 | 도구 준비와 새 잡기로 누름 시작을 선택 |
| 정지한 채 누르고 있기 | 닫힘 뒤 바로 down을 유지할 수 있음 | 이동 인계 전은 down 없음. 후보 만료와도 구분 필요 | 도구 준비·잡기 완료 뒤 latch down 유지 가능 |
| 긴 드래그 | 닫힘 유지 필요 | 닫힘 유지 필요 | 손가락을 풀 수 있으나 별도 종료 주기 필요 |
| down 이전 포기 | 닫힘 확정 전에는 버튼 down을 보내지 않음 | 인계/클릭 확정 전 취소·만료 가능 | 도구 준비 취소는 down 없음 |

G0를 B1의 별칭으로 쓰지 않는다. OS에 영향을 주기 시작하는 때와 초기 이동 처리, 취소 가능한 구간이 다르다. 실제 버튼도 앱에 따라 누름·해제·hover 시점에 반응할 수 있다. WPF ClickMode는 이 세 시점을 구분한다. 그러므로 G0의 down 뒤에는 아직 up이 없다는 이유로 ‘앱에 아무 영향도 없었다’고 볼 수 없다. [ClickMode 공식 문서](https://learn.microsoft.com/en-us/dotnet/api/system.windows.controls.clickmode?view=windowsdesktop-10.0)

관찰 불확실성·중지 때 up을 보내면 버튼이 남는 것을 줄일 수 있지만, 해제에 반응하는 앱에서는 클릭·선택 확정·드롭이 발생할 수 있다. down에 이미 반응했다면 그 영향도 남는다. 이를 취소나 롤백으로 설명하지 않는다. 닫힘/열림의 흔들림 억제, 후보 동안의 커서 고정과 재기준, 같은 관찰의 이동/열림 처리, 유지 근거 소실 정책은 G0에서도 별도로 고정해야 한다.

다음 선행 비교는 두 장면으로 좁힌다. ① 작은 목표 선택과 같은 항목의 짧은 드래그를 번갈아 수행해 G0의 우발 드래그·목표 이탈과 B1의 시작 지연·폐기된 이동을 본다. ② 기존 앱에서 실제로 정지 누름 동안 동작하는 컨트롤을 사전 확인하고, 정상 유지·해제와 중간 중지를 비교한다. 대상 앱을 새로 만들거나 지금 실행한 것은 아니다.

G0가 유력하면 유지형 기준 후보의 정의와 대응 두 손 조건을 먼저 개정한다. 기존 B1/B2 또는 A/B/C 회차에 G0를 몰래 섞지 않는다. 이 선행 검토는 G0의 우월성·RGB 인식 가능성을 입증한 결과가 아니다.

[R2 팀 참조 조건](facilitator-guide.md)은 정상 중간구간·필수 근거 관찰불가·후보 마감·같은 관찰의 이동/열림을 구분해 G0 왼쪽 버튼의 출력만 고정한다. 모든 기본 동작이나 대응 두 손 조건을 완성한 참조가 아니며 제품 채택 결과도 아니다.

## 후보 한 번을 소비하는 규칙

각 요청은 시작한 손과 그때의 작업 맥락에 속한다. 시작 신호의 닫힘을 다른 손의 열림과 합치지 않는다. 도구 선택에 사용한 신호를 도구를 닫은 뒤 대상 앱 클릭이나 잡기로 다시 사용하지 않는다.

| 사건 순서 | 제안한 처리 | 미결정 또는 검증할 내용 |
| --- | --- | --- |
| 닫힘 후보 → 정상 열림 | G2에서 클릭 한 번 | 후보 인정·열림 확정의 관찰 조건 |
| 닫힘 → 오래 유지 → 후보 만료 → 열림 | 클릭 없음. 뒤늦은 열림은 만료된 시도의 잔여 동작으로 소비 | 오래 유지의 의미와 만료 시간 |
| 닫힘 → 취소 확정 → 열림 | 클릭 없음. 열림만으로 취소를 되돌리지 않음 | 관찰 가능한 취소 신호 |
| 닫힘 → 움직임 → 드래그로 인계 → 열림 | 드래그 종료만 실행. 미완료 클릭은 다시 실행하지 않음 | 인계 문턱, 시작 전 이동과 클릭 위치 |
| 닫힘 → 추적 소실 → 열린 손으로 복귀 | 누락된 관찰을 열림으로 추정하지 않음. 후보를 폐기하고 보류. 명시적 세션 재진입을 소비한 뒤 새 포인터 기준과 새 요청 필요 | 해제·복구 표시와 다시 시작하는 비용 |
| 닫힘 → 손 교차·신원 불확실 → 열림 | 서로 다른 손의 사건을 합치지 않고 후보 무효화 | 손 신원 확인 방법 |
| 도구 선택 → 손이 아직 닫힘 → 대상 앱 복귀 | 이미 유지 중인 닫힘을 새 잡기로 보지 않음 | 다음 독립 요청을 설명하는 표시 |
| 취소/만료와 열림이 같은 처리 시점에 관찰됨 | 취소/만료를 우선하고 해당 시도를 종료 | 마감 경계·관찰 시각 기준을 실험 전에 고정 |

정상 G2 클릭의 열림은 해당 요청의 완료이며, 이후 새로운 닫힘이 오기 전까지 추가 클릭이 없다. 또 다른 전신 중립 자세를 매번 요구하지 않는다. 반면 취소·만료·소실 당시 손이 아직 닫혀 있었다면 그 손이 새로 열린 것을 확인하기 전에는 다음 닫힘을 받을 수 없다.

일반 후보의 취소·만료 후 다시 준비하는 것과 추적 소실 뒤 복귀는 다른 절차다. 소실 뒤에는 새 열림만으로 바로 클릭을 받지 않는다. 추적과 손 신원을 다시 확인하고 명시적인 세션 시작 요청을 소비한 뒤 현재 손 위치를 새 포인터 기준으로 잡는다. 시작 요청의 잔여 동작은 클릭으로 전달하지 않으며 이후 독립된 새 요청부터 받는다.

## 취소 방식에서 먼저 반증할 것

‘휴식 영역으로 손을 옮기면 클릭 후보 취소’라는 안은 B1의 ‘손을 움직이면 드래그 시작’과 충돌할 수 있다. 같은 변위를 취소와 드래그로 동시에 해석하지 않는다. 다른 영역·신호를 쓰거나, B1의 드래그 시작 문법을 바꾸거나, 후보 만료를 취소로 이용하는 안을 따로 비교해야 한다.

오래 유지하는 것을 만료·취소로 삼으면 기다림과 손가락 부담이 늘 수 있다. 반대로 오래 유지하면 도구를 여는 방식은 취소와 또 다른 의미를 갖는다. 기본 규칙을 먼저 정하고 개인 설정이 이 의미를 조용히 바꾸지 않도록 한다. 타이핑이나 긴 드래그 때문에 생긴 자연스러운 멈춤을 무조건 클릭 취소 의도로 해석하지 않는다.

후보 중 보이는 커서를 잠시 고정하는 안은 목표 이탈을 줄일 수 있지만, 잘못된 후보가 잦으면 이동을 끊는다. 고정 유무와 길이는 별도 요인으로 비교한다. OS down/up을 보낼 위치는 그 순간 사용자가 보는 커서 위치와 일치시킨다. 과거 목표 위치를 조용히 클릭하지 않는다.

## 더블클릭은 재준비 규칙과 함께 검토한다

두 번의 독립 클릭을 빠르게 수행하는 방식과, 한 번의 별도 요청이 두 클릭을 생성하는 방식은 다른 사용자 규칙이다. 둘을 섞어 앞선 단일 클릭에 두 클릭을 덧붙이면 세 번 클릭이 될 수 있다. 선택한 규칙의 전체 요청을 소비하고, 이전 미완료 단일 클릭이 남지 않도록 검토한다.

Windows는 현재 더블클릭 시간과 클릭 위치 사각형을 사용한다. 두 클릭 사이의 시간만 맞추고 손의 이동을 무시하면 충분하지 않다. 시스템 설정을 제스처의 인간공학적 최적 시간으로 해석하지 않으며, 두 손가락 동작 주기·확정 대기·다시 준비하기가 그 안에서 가능한지를 실제 센서 단계에 측정한다.

출처: [GetDoubleClickTime](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getdoubleclicktime), [GetSystemMetrics의 더블클릭 사각형](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getsystemmetrics).

## 구현 전 상태 카드로 확인할 장면

[진행 안내의 R1 비교](facilitator-guide.md)는 공통 G2·보이는 커서 고정 조건에서 B1/B2의 같은 후속 관찰과 실패 장면을 나란히 검토한다. B1 휴식/인계 경계와 유지 근거 미판정의 특정 참조 선택을 고정한 것이며 제품 정책 선정 결과가 아니다. B2에서도 새 종료 후보 뒤의 정상 열림은 드롭이므로, ‘손을 풀어도 유지’라는 표현에는 후보가 없는 맥락이 필요하다.

시작 요청이 끝나기 전에 클릭 요청을 한다. 클릭하려다 멈춘다. 오래 유지하고 푼다. 클릭 후보 중 손을 움직인다. 드래그 준비를 포기한다. 손을 가렸다가 닫힌 채 돌아온다. 다른 손을 대신 넣는다. 같은 목표에서 두 번 클릭한다. 도구 메뉴를 닫은 동작을 유지한다.

각 장면에서 참가자가 예상한 결과, 진행자가 적용한 규칙, 서로 다른 해석을 남긴다. 운영자가 참가자의 마음을 알아서 적절히 취소해 주면 문법의 모호함이 가려진다. 화면에는 후보·실행·취소의 차이를 보여 주되, 이 모사가 실제 인식 지연과 클릭 신뢰성을 입증한다고 기록하지 않는다.
