# MANUX 마스터 플랜

기준일: 2026-10-29. 이 문서는 착수보고와 GitHub 인수인계용 개발 계획이다. **인수인계 준비에서는 앱 기준선을 보존했으며, 아래 내용은 담당자가 자기 브랜치에서 수행할 과제다.** 팀원과 에이전트는 배정된 범위에 따라 개발을 시작한다. [Jira 조회 기록](jira-snapshot-20261029.json)에서 MANUX 이슈 SCRUM-5~SCRUM-16은 모두 `해야 할 일`이다. 문서 작성은 이슈 완료나 Jira 변경을 뜻하지 않는다.

## 1. 제품 목표와 현재 문제

웹캠으로 손 모양을 읽고 사용자가 선택한 동작을 명령에 연결하는 입력 인터페이스를 만든다. 이번 기준선은 Windows Edge/Chrome에서 **앱 내부 영상**을 제어한다. 장기 목표는 키보드·마우스와 함께 쓰는 사용자 정의 손 모양·액션 바인딩, Electron 기반 데스크톱 HMI, 별도 Android 앱이다. Android는 Electron 앱을 그대로 실행하는 확장이 아니며 플랫폼별 구현과 권한 검증이 필요하다.

사용자는 2026-10-29에 “네 동작을 한꺼번에 등록하면 부담이 크고 실제 등록도 제대로 되지 않는다”고 보고했다. 요구는 **원하는 동작 하나 선택, 그 동작만 등록, 확인 후 저장**으로 바뀌었다. 현재 코드에 각도별 등록이 있다는 사실과 실제 사용자가 성공했다는 사실을 구분한다. 등록 실패의 정확한 원인은 아직 재현·확정하지 않았다.

| 구분 | 현재 확인한 내용 | 발표에서 사용할 표현 |
| --- | --- | --- |
| 구현된 기준선 | 기본 네 명령, 1080p 요청, 시간 안정화, 선택적 ±10초 반복, 책상/소파 프로필, 각도별 등록 화면 | 기능 연결이 있는 프로토타입 |
| 자동 검증 | 직전 126개 단위 테스트와 합성 입력을 포함한 브라우저 흐름 시험 통과 | 코드·상태 전이 검증 근거 |
| 사용자 문제 | 일괄 등록 부담과 실제 등록 실패 보고 | 우선 해결할 제품 문제, 원인 조사 필요 |
| 아직 없는 기능 | 동작별 독립 등록, 임의 손 모양 추가, 액션 변경, Electron, OS 제어 | 다음 개발 또는 후속 확장 |
| 기술 방식 | 고정 MediaPipe 손 추적 + 관절 특징 기반 개인화 | 개인화·보정, 사전학습 모델 파인튜닝 아님 |

실제 거리별 인식률, 실물 웹캠 각도 정확도, 전체 반응 시간 개선 수치는 아직 확보하지 않았다. 모델 점수 70%를 정확도 70%라고 표현하지 않는다.

## 2. 우선순위와 완료 범위

### P0: 이번 2주 핵심

1. 실제 웹캠에서 등록 실패를 재현하고, 카메라 품질·각도 판정·수집·모델 구성·별도 확인·저장 중 멈춘 단계를 기록한다.
2. 기본 네 동작 중 **하나만** 골라 등록·별도 확인·저장한다. 다른 세 동작을 끝내야 저장되는 조건을 제거한다.
3. 책상과 소파 등록은 계속 분리한다. 한 동작을 재등록해도 다른 동작·다른 환경·다른 사용자의 유효 등록은 보존한다.
4. 실패·취소·저장 오류에서는 기존 등록을 보존한다. 부분 등록의 미등록·불확실·중립 입력은 명령을 만들지 않는다.
5. 실물 사용에서 등록 완료율·소요 시간·재시도와 명령 성공·오실행·반응 시간을 평가한다.

각도 다양성은 유지하되, 현재의 5방향 강제 절차·유지 시간·허용 범위를 검증 없이 고정하지 않는다. 먼저 한 동작 단위로 분리하고 실제 실패 로그로 조건을 조정한다. 기준을 낮추는 변경은 오실행 비교와 함께 검토한다.

### P1: P0 인수 후 확장 후보

- 이름이 있는 사용자 정의 **정적인 한 손 모양**을 등록한다. 예: 사용자가 정의한 `rock`.
- 모양의 ID와 명령의 ID를 분리하여, 등록된 모양 하나에 앱 내부의 재생·정지·±10초 중 하나를 연결한다.
- 기존 모양과 충돌하면 원인을 안내하고 저장을 보류한다. 미연결 모양은 인식 표시만 하고 실행하지 않는다.
- 사용자가 요청한 기능이며 다음 설계에 포함한다. 기존 Jira의 확정 완료 조건에는 아직 없으므로 [변경안](jira-change-proposal.md)으로 구분한다.

### 후속 범위

Electron 패키징, 시스템 음량, Alt+Tab, 마우스 커서, PC 종료, 임의 매크로, 다른 앱 제어는 [데스크톱 HMI 설계](desktop-hmi.md)의 후속 범위다. 이번 2주에 모두 완성한다고 약속하지 않는다. 흔들기·원을 그리기 같은 시간적 모션도 정적 손 모양 등록과 별도 과제다.

키보드와 제스처를 함께 쓰는 입력 조건, Android의 카메라·앱 제어 계층도 후속 설계다. 사업성 발표에서는 초기 고객과 대안, 지불 의사 가설을 [조사 근거](presentation/business-research.md)에 따라 구분한다. 손목터널증후군 예방·치료나 실제 시장 점유율을 이 프로토타입의 검증 성과로 주장하지 않는다.

## 3. 원하는 사용자 흐름

1. 사용자와 책상/소파 환경을 선택한다.
2. 기본 동작 목록에서 등록할 모양 하나를 선택한다. 다른 모양 등록은 선택 사항이다.
3. 카메라를 보며 그 모양의 필요한 방향을 수집한다. 부족한 조건과 진행 상태를 표시한다.
4. 새 수행으로 같은 모양을 확인하고, 중립·다른 모양에서 명령을 거부하는지 점검한다.
5. 해당 동작의 검증된 등록만 저장한다. 사용자가 제어를 켜면 사용한다.
6. P1에서는 `새 동작 추가`로 이름과 모양을 등록한 뒤 지원 액션에 연결한다.

`rock`은 미리 정해진 모델 라벨일 필요가 없다. 관절 특징 예시를 사용자가 붙인 별도 ID에 저장하는 설계가 필요하다. 현재의 `POSES` 목록, 전체 클래스 필수 검사, 고정 명령 매핑은 이를 지원하지 않으므로 R3·R4·R5·R2가 계약을 맞춰 단계적으로 바꾼다. 이름만 추가하거나 기존 제스처 라벨을 강제로 붙이는 것으로 완료하지 않는다.

## 6. 10영업일 계획

Jira의 전용 스프린트 조회로 확인한 `SCRUM Sprint 0`은 활성 상태이며 기간은 **2026-10-29 09:07~2026-11-12 09:07 KST**다. 아래는 **약 2주·10영업일의 작업량 가정**이며 날짜 범위의 영업일 수를 계산한 값이 아니다. 실제 출석일·가용 시간을 D1에 맞춘다. 발표 시각과 일정은 팀 운영 공지를 우선한다.

| 시점 | 공통 결과 | 담당 중점 |
| --- | --- | --- |
| D1~D2 | 기준선 재현, 사용자 실패 로그, 계약·평가 조건 확정 | R1 입력 품질, R4 막힌 단계, R3 단일 클래스 거부, R5 버전, R2 기존 명령 불변조건 |
| D3~D4 | 한 동작의 수집·검증·저장 모듈 | R3 모델, R4 흐름, R5 부분 저장을 중심으로 통합 |
| D5 | P0 첫 전체 시연 | 한 동작만 등록해 제어하고 새로고침·재등록·취소를 확인 |
| D6~D8 | 실물 비교·결함 수정, P1 착수 여부 판단 | 각 담당 평가와 교차 리뷰. P0 미통과면 P1 일정 보류 |
| D9~D10 | 기능 동결, 다른 PC 실행, 발표 증거 | 회귀·설치·리허설, 개인별 문제 해결 기록과 알려진 한계 |

완료 시간·명령 성공률·오실행 목표값은 D2의 기준선 이후 **시험 전에** 정하고 기록한다. 목표값을 실측 성과처럼 쓰거나 결과를 본 뒤 유리한 조건으로 바꾸지 않는다.

## 7. 공통 인수 기준

- 기본 네 명령과 반복 OFF/ON 동작이 회귀 없이 유지된다.
- 기본 동작 하나를 등록하면 다른 동작을 요구하지 않고 독립 저장·사용할 수 있다.
- 미등록·미연결·중립·불확실 입력은 명령이 없고, 개인 판정 거부를 공통 모델로 우회하지 않는다.
- 재등록·취소·검증 실패·저장 실패가 다른 유효 등록을 훼손하지 않는다.
- 카메라 종료·탭 이탈·사용자/환경/설정/바인딩 변경에서 진행 중 판정과 반복을 해제한다.
- 작성자 외 리뷰, 재현 명령, 조건·표본 수가 있는 결과, 남은 한계를 PR에 남긴다.
- 등록·평가 세션을 분리하고, 합성 입력 시험과 실제 웹캠 시험을 구분한다.
- 실제 등록 문제가 재현·해결·재확인되기 전에는 등록 사용성 검증 완료로 표시하지 않는다.

평가 상세는 [기존 팀 계획](team-plan.md), 자동 검증의 범위는 [검증 기록](verification.md), 개인별 포트폴리오 증거는 [핵심 역량](career-skills.md)을 참고한다. 최신 사용자 요구와 기존 Jira 범위가 다른 항목은 [Jira 변경안](jira-change-proposal.md)을 따른다.
