# MANUX 사업 관점 발표 근거

조사 기준일: **2026-10-29, Asia/Seoul**. 발표 본문은 짧은 문제·제품·고객·차별점으로 구성하고, 아래 근거와 한계는 발표 노트·질의응답에서 설명한다. 사실, 제품 방향, 검증 전 가정을 구분한다. 현재 앱 구현 범위는 [README](../../README.md), 개발 우선순위는 [마스터 플랜](../master-plan.md)을 따른다.

## 1. 제안하는 사업 설명

**기존 PC와 웹캠에서, 필요한 순간에 손동작과 키보드를 함께 쓰는 개인화 입력 도구**를 제품 방향으로 제시한다. 텍스트 입력·정밀 작업은 기존 입력에 맡기고, 재생·이동·발표·반복 명령처럼 짧고 구분 가능한 행동을 손동작에 연결하는 가설이다.

현재 구현은 네 고정 손 모양으로 **앱 내부 영상**을 제어한다. 키보드 조합과 제스처의 결합, 사용자 정의 모양·자유 바인딩, 외부 발표 앱 제어, Electron·OS 명령은 아직 제품 방향이다. 발표에서 이미 작동하는 기능처럼 보여주지 않는다.

### 데스크톱과 Android 확장

Electron은 JavaScript·HTML·CSS로 Windows·macOS·Linux 데스크톱 앱을 만드는 경로다. Android 앱이 같은 패키지로 만들어지는 것은 아니다. Android에서는 별도 카메라·생명주기·모델 실행과 사용자 흐름이 필요하며, MediaPipe의 공식 Android Gesture Recognizer 예제를 출발점으로 검토할 수 있다. [Electron 공식 문서](https://www.electronjs.org/docs/latest/), [MediaPipe Android 예제](https://github.com/google-ai-edge/mediapipe-samples/blob/main/examples/gesture_recognizer/android/README.md)

Android 확장은 ‘휴대폰에서 PC를 조작하는 보조 입력기’와 ‘Android 자체를 조작하는 입력 도구’ 중 어느 제품인지 먼저 정해야 한다. 후자는 접근성 서비스 등 플랫폼 API의 역할·허용 범위·사용자 활성화 조건을 별도 검토해야 한다. 현재 웹 데모나 Electron 계획만으로 Android 시스템 제어가 구현됐다고 설명하지 않는다. [Android AccessibilityService API](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService)

### 초기 고객 가설

| 후보 | 사용 순간 | 먼저 확인할 질문 |
| --- | --- | --- |
| PC로 영상·강의를 보는 사람 | 떨어진 자리에서 재생·일시정지·구간 이동 | 키보드·휴대폰·리모컨보다 이 방식을 다시 선택하는가 |
| 발표·수업을 진행하는 사람 | 키보드 가까이에 가지 않고 간헐적 명령 | 클릭커·음성보다 실수와 준비 부담이 적은가 |
| 반복 작업을 수행하는 PC 사용자 | 자주 쓰는 명령을 짧은 모양·키 조합에 연결 | 기존 단축키·매크로보다 기억·실행·복구가 쉬운가 |

앞의 고객은 **검증 전 가설**이다. 현재 데모와 가장 가까운 영상 제어부터 테스트하고, 발표·업무 명령은 지원 앱과 실제 워크플로를 확인한 뒤 넓힌다. 특정 질환 환자 전체나 장애인 전체를 동일한 사용 능력·요구를 가진 고객으로 묶지 않는다.

## 2. 손목터널증후군을 설명할 수 있는 범위

NHS는 손목터널증후군(CTS)을 손목에서 정중신경이 압박되는 상태로 설명한다. 저림·감각 저하·통증 등이 나타날 수 있으며, 반복적으로 손목을 굽히거나 강하게 쥐는 활동을 여러 위험 요인 중 하나로 제시한다. NHS 페이지 검토일은 **2024-04-17**이다. [NHS 공식 설명](https://www.nhs.uk/conditions/carpal-tunnel-syndrome/)

AAOS의 **2024-06-11** 가이드라인 발표는 많은 키보드 사용과 CTS의 관련성을 강하게 뒷받침하는 근거가 없다고 명시한다. 이는 신뢰할 근거가 부족할 때의 전문가 합의 맥락이므로, 모든 컴퓨터 사용의 무해함이 증명됐다는 뜻으로도 확대하지 않는다. [AAOS 2024 공식 발표](https://www.aaos.org/aaos-home/newsroom/press-releases/carpal-tunnel-syndrome-aaos-updates-clinical-practice-guideline/), [AAOS/ASSH 지침 요약, 2025년 4월 인쇄판](https://pmc.ncbi.nlm.nih.gov/articles/PMC11928260/)

| 발표 표현 | 판단 |
| --- | --- |
| “입력 과정의 불편과 부담을 줄일 대안을 탐색합니다.” | 제품 가설로 가능. 실제 사용 비교가 필요 |
| “손목터널증후군은 손목의 신경 압박과 관련된 질환입니다.” | 위 공식 근거로 설명 가능 |
| “키보드를 많이 쓰면 손목터널증후군이 생깁니다.” | 인과관계로 단정하지 않음 |
| “MANUX가 손목터널증후군을 예방·치료합니다.” | 임상 근거 없음. 사용하지 않음 |
| “제스처 입력은 손목·팔의 피로가 없습니다.” | 사용하지 않음. 제스처 자체의 부담도 평가 |

CTS는 문제 배경이나 질의응답의 한 문장으로 제한하는 편이 적합하다. 현재 제품의 효용을 입증할 직접 지표는 **작업 완료 시간, 오실행, 등록 부담, 반복 사용 의향, 사용 중 느낀 불편**이다. 질환 예방·치료 효과를 측정한 것으로 표현하지 않는다.

## 3. 제스처도 오래 사용하면 피로할 수 있다

Microsoft의 Mixed Reality 설계 가이드는 손을 계속 들고 있거나 장시간 공중 탭을 반복하면 근육 피로가 쌓일 수 있다고 설명하고 지속적 반복 제스처를 피하도록 권한다. 문서 갱신일은 **2021-10-19**이며, 헤드셋 환경의 설계 지침이므로 MANUX의 특정 피로 감소율을 입증하지 않는다. [Microsoft Learn, Comfort의 Arm positions](https://learn.microsoft.com/en-us/windows/mixed-reality/design/comfort#arm-positions)

이를 바탕으로 한 **설계 추론**은 짧은 간헐적 손동작, 팔을 편한 위치에 둘 수 있는 모양, 키보드·마우스와 병행 가능한 방식이다. 모든 입력을 제스처로 대체하는 방향이나 손을 오래 유지하는 등록 절차는 검증 없이 편안하다고 설명하지 않는다. 현재의 일괄 등록 실패·부담 보고는 이 사용성 가설을 실제로 점검해야 한다는 근거다.

## 4. 시장 배경으로 사용할 수 있는 공식 숫자

NIA의 **2025년 인터넷이용실태조사 최종보고서** 수정본을 확인했다. 게시일 **2026-03-31**, 수정 공지 **2026-05-26**. 보고서 p.116의 수치를 PDF 실제 페이지 134에서 시각적으로 확인했다. [NIA 공식 보고서 게시 페이지](https://nia.or.kr/site/nia_kor/ex/bbs/View.do?bcIdx=29198&cbIdx=99870&parentSeq=29198), [공식 PDF 다운로드](https://www.nia.or.kr/common/board/Download.do?bcIdx=29198&cbIdx=99870&fileNo=3)

| 수치 | 기준·분모 | 해석 범위 |
| --- | --- | --- |
| **78.7%** | 2025년 7월, 대한민국 전체 가구의 컴퓨터 보유율 | 데스크톱·노트북·태블릿 포함 |
| **55.4%** | 전체 가구의 노트북 컴퓨터 보유율 | 복수응답, 가구 단위 |
| **53.6%** | 전체 가구의 데스크톱 컴퓨터 보유율 | 복수응답, 가구 단위 |

슬라이드에서는 **“국내 가구 55.4%가 노트북 보유”**처럼 한 수치만 크게 표시하고, **“PC 이용 기반을 보여주는 수치이며 MANUX 구매 고객 수는 아님”**을 노트에 둔다. 노트북과 데스크톱 보유율은 중복되므로 합산하지 않는다. 이 자료는 Windows 비중, 웹캠 장착, 제스처 사용 의향이나 지불 의향을 알려주지 않는다.

보고서 p.131의 컴퓨터 이용률 76.0%도 확인했으나 만 3세 이상 인구와 태블릿을 포함하는 넓은 지표이므로, 초기 PC 고객 규모 계산에는 사용하지 않는 편이 좋다. 산업용 패널·공장 자동화·자동차까지 포함하는 HMI 시장 금액도 이 제품의 TAM으로 가져오지 않는다.

## 5. 시장 규모는 도달 가능한 고객부터 계산

현재 확정할 수 있는 유료 고객 수·지불 의향·실제 가격은 없다. 큰 산업 시장액에 임의 점유율을 곱한 수치를 매출 전망으로 제시하지 않는다. 초기 채널과 지원 워크플로가 정해진 뒤 다음처럼 계산한다.

```text
유료 고객 수 = 도달한 대상 사용자 수
             × 설치 전환율
             × 일정 기간 활성 유지율
             × 유료 전환율

기간 매출 = 해당 기간 유료 고객 수 × 같은 기간의 실제 결제 단가
```

**계산 방식 설명용 가정 예시:** 10,000명에게 도달하고 설치 20%, 4주 활성 유지 30%, 유료 전환 10%라면 유료 고객은 60명이다. 1회 결제 20,000원을 가정하면 첫 결제 매출은 1,200,000원이다. **모든 입력은 임의 가정이고 가격·수요·시장 규모·매출 예측이 아니다.** 일회성 매출을 월 반복 매출이나 연간 구독 매출로 바꾸어 부르지 않는다. 이 예시는 발표 노트·질의응답의 계산 설명에 적합하며, 본문에 넣으면 ‘가정 예시’ 표기를 유지한다.

TAM/SAM/SOM 형식이 요구되면 TAM은 넓은 PC 입력 수요 범주, SAM은 지원 OS·장치·워크플로 조건을 충족하는 집단, 초기 SOM은 실제로 도달·설치·유지·결제까지 확인한 집단으로 정의한다. 현재 SAM/SOM 수치는 미산정이다. 공식 PC 보급률을 유료 사용 의향과 곧바로 연결하지 않는다.

### 가격·사업 모델 가설

- 기본 명령 체험 후 앱별 동작·프로필·자동화 기능을 판매하는 소프트웨어 모델을 검토할 수 있다.
- 발표·교육 공간에는 설치·관리·지원에 대한 기관 라이선스가 별도 가설이 될 수 있다.
- 가격과 구독 필요성은 아직 검증하지 않았다. 무료 단축키·음성·리모컨보다 지속적으로 선택할 이유를 먼저 확인한다.
- 초기 데모 참가자의 호응과 실제 결제·지속 사용을 구분한다.

### 초기 도달 채널과 인터뷰 질문

교육 과정·수업 발표 참가자, PC 영상 학습 사용자, 생산성 도구 커뮤니티를 초기 모집 채널 후보로 둔다. 실제 모집·게시·연락은 아직 하지 않았고, 채널의 규모나 전환율도 확인하지 않았다. 기관 구매를 가정하려면 실제 사용자와 설치·구매 결정자가 같은 사람인지 확인한다.

- 최근 비슷한 상황에서 어떤 명령을 몇 번 실행했고 무엇이 불편했는가.
- 지금 사용하는 단축키·리모컨·음성 입력이 있는데도 바꾸려는 이유가 있는가.
- 카메라를 켜고 동작을 등록하는 수고를 감수할 만큼 자주 겪는가.
- 어떤 앱·명령이 빠지면 계속 쓰지 않겠는가.
- 무료 기본 기능과 유료 앱별 설정·자동화 후보 중 무엇에 비용을 지불할 이유가 있는가.

먼저 실제 행동 사례를 묻고 나서 제품을 보여준다. 유도 질문으로 받은 호감 표현을 수요 검증이나 결제로 집계하지 않는다.

## 7. 차별점은 검증할 약속으로 제시

제안 문장: **“기존 웹캠과 키보드에, 내가 고른 손동작을 더합니다.”**

핵심 가설은 별도 센서 구매 없이 시작하고, 조용한 손 입력을 필요한 명령에만 쓰며, 개인이 편한 모양과 액션을 연결하는 경험이다. 현재 임의 모양·액션 연결은 미구현이고, 웹캠은 조명·가림·거리·손 크기에 영향을 받는다. 등록 부담과 원치 않는 실행을 줄이지 못하면 장비가 적다는 장점만으로 고객이 유지되지 않을 수 있다.

소프트웨어가 기존 장비에서 실행된다는 사실은 **전체 도입 비용 0원**을 뜻하지 않는다. 호환 장비, 초기 설정·등록, 사용자 교육, 오류 복구에 시간이 든다. 진짜 차별성은 같은 작업에서 설치·첫 성공까지 시간, 반복 사용, 오류와 복구, 기존 방식 대비 선택 비율로 확인한다.

## 8. 2주 동안 사업 가설을 확인할 방법

이는 아직 수행하지 않은 계획이다. 개발 검증과 연결하되 고객 인터뷰를 제품 성능 측정으로 대신하지 않는다.

1. 영상 사용 상황 한 가지를 정하고 기존 키보드/리모컨 방식의 절차와 불편을 관찰한다.
2. 동작 하나의 등록 완료 시간, 도움 요청, 재시도·포기를 기록한다. 미리 정한 소수 참가자에게 같은 순서를 강요하지 않고 비교 순서 효과를 고려한다.
3. 같은 영상 과제에서 기존 방식과 MANUX의 완료 시간·오실행·복구·주관적 불편을 비교한다.
4. 체험 직후 호감도와 며칠 뒤 자발적 재사용을 분리한다. 실제 외부 참가자 수와 수행 조건을 보고한다.
5. 유료 기능 가설과 가격 선택 질문을 검토한다. 응답한 지불 의향은 실제 결제 성과로 기록하지 않는다.

현재 사용자 등록 실패가 P0인 이유는 사업적으로도 명확하다. 등록을 끝내지 못하면 명령의 편리함을 체험할 기회가 없기 때문이다. 먼저 **한 동작의 첫 성공**을 만들고, 이후 사용자 정의 동작·키보드 결합·앱별 바인딩으로 확장하는 순서가 합리적이다.
