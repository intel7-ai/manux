# 브라우징 중 커서 고정 (2026-11-04)

엄지+검지 핀치로 페이지를 스크롤하는 동안 커서를 **그 자리에 고정**하고, 앱이 스크롤 영역을 알려 주는 경우에는 영역의 정중앙으로 옮긴다.
한 페이지 안에도 독립적으로 스크롤되는 영역(label)이 여럿 있고(사이드바, 목록, 메시지 영역 …) 휠은 **커서 아래 영역**을 움직이므로,
브라우징 대상은 "커서가 올라가 있는 영역"이다. 다른 영역을 브라우징하려면 커서를 그 영역으로 옮겨 두고 핀치로 잡으면 된다.

| 구분 | 동작 |
| --- | --- |
| 대상 정하기 | 사용자가 커서를 올려 둔 곳이 대상이다. 앱이 스크롤 영역을 알려 주면(Windows UI Automation, `src/scroll_target.py`) 커서 아래의 가장 안쪽 스크롤 영역을 쓴다 |
| 정중앙 이동 | 알려 준 영역이 **창의 일부(창 면적의 60% 미만, `scroll_center_max_fraction`)**일 때만 그 영역 정중앙으로 옮긴다(이미 24px 안이면 옮기지 않음). 목록·사이드바 같은 칸이 해당된다 |
| 옮기지 않는 경우 | ① 영역이 창의 대부분인 경우(페이지 자체. 안쪽에 앱이 알려 주지 않는 스크롤 영역이 더 있을 수 있어, 페이지 가운데로 옮기면 그 영역을 놓친다) ② 앱이 아무 영역도 알려 주지 않는 경우(웹앱의 패널은 대부분 그렇다). 이때는 **커서가 있는 자리에 그대로 둔다** |
| 연속 브라우징 | 한 번 정한 자리(첫 잡기에서 커서가 있던 곳, 또는 정중앙으로 옮겼다면 그 정중앙)를 **연속 브라우징의 기준점**으로 기억한다. 마지막 브라우징 후 4초(`scroll_series_gap`) 안에 다시 잡으면, 그 사이 손을 되돌리며 커서가 끌려갔더라도 기준점으로 되돌려 보낸다. 앱이 영역을 알려 주지 않아도 된다 |
| 새 기준점 | 마지막 브라우징 후 4초가 지났거나, 사용자가 다른 label로 커서를 옮겨 **0.4초(`scroll_series_dwell`) 이상 멈춘 뒤** 잡으면 그 자리가 새 기준점이다. 커서가 아직 움직이는 중에 잡으면 손을 되돌리다 끌려간 것으로 보고 기준점으로 되돌린다 |
| 고정 | 어느 경우든 잡는 순간부터 잡고 있는 동안, 관성으로 흘러가는 동안, 놓은 뒤 1.2초(`scroll_session_hold`) 동안 커서 이동 명령을 무시한다. 손을 되돌려도 커서는 안 움직이고, 1.2초 안에 다시 잡으면 같은 영역의 연속 브라우징이다 |
| 해제 | 1.2초 뒤 다시 손을 따라 커서가 움직인다(상대 이동이라 튀지 않음). 그때 커서를 다른 영역에 올려 두고 잡으면 그 영역이 새 대상이다 |
| 끄기 | `scroll_center_cursor`: false (고정과 이동 모두 끔). UI Automation만 끄려면 `scroll_target_uia`: false. 예전처럼 영역을 못 찾을 때 창 가운데로 옮기려면 `scroll_center_fallback_window`: true |

- 코드: `src/scroll_target.py`(영역 찾기, 별도 스레드·캐시), `src/window_probe.py`(창 가운데, 선택 사항), `MouseController._begin_browse` / `_browse_lock`. `main.py`가 `mouse`에 연결한다.
- 응답 시간: UI Automation은 느릴 수 있어서 제어 루프에서 부르지 않는다. 별도 스레드가 커서 위치 알림(`hint`)을 받아 커서가 멈춘 곳의 영역을 미리 찾아 두고, 핀치 순간에는 캐시에서 바로 답한다. 캐시에 없으면 최대 0.15초(`scroll_target_wait`)만 기다린 뒤 "찾지 못함"으로 처리한다.

## 2026-11-04 브라우저에서 독립된 label이 개별 브라우징이 안 됐던 원인
- 로그의 브라우징 대상은 전부 `window:Chrome_WidgetWin_1`(창 가운데로 대신하는 경우)이었다. 같은 Chrome 페이지(BambooChat)의 UI Automation 트리를 직접 열어 보니, 사이드바의 목록 두 곳은 스크롤 영역(`ListControl`, 세로 스크롤 가능)으로 알려 주지만 **메시지 영역은 평범한 `GroupControl`이고 위로 올라가 문서(Document)까지도 스크롤 가능으로 표시되지 않았다**. 그래서 영역을 못 찾았고, 그때마다 창 가운데로 커서를 보내 다른 label을 대상으로 만들었다.
- 수정: 영역을 못 찾거나 영역이 페이지 크기일 때는 **커서를 옮기지 않고 그 자리에 고정**만 한다(창 가운데 대체는 기본 꺼짐). 커서를 올려 둔 label이 곧 대상이 된다.
- 한계: 앱이 알려 주지 않는 label에서는 정중앙으로 옮기지 못한다(커서는 사용자가 둔 자리에 고정). 알려 주는 칸(사이드바 목록 등)에서만 정중앙 이동이 동작한다. Chrome은 접근성 트리를 처음 요청받을 때 만들기 시작해서 몇 초 걸릴 수 있다. **브라우저 안의 실제 핀치 브라우징은 아직 직접 확인하지 못했다.**
- 대가: 브라우징을 끝내고 바로 링크로 가려면 놓은 뒤 1.2초는 커서가 움직이지 않는다.
- 이 기능은 핀치로 스크롤하는 팔 모드("손바닥 · Dan")에서 동작한다. 검지 포인터 모드는 스크롤 그랩이 꺼져 있다.
- 로그: 프레임별 `browse`(`[x, y, "region:…"|"page:…"|"window:…"|"kept"]`), 이벤트 로그 `scroll_center:x,y:region|window`.

## 연속 브라우징에서 처음 자리로 돌아가기 (2026-11-04)
- 앱이 label의 경계를 알려 주지 않아도 쓸 수 있다: 첫 잡기에서 사용자가 커서를 올려 둔 자리를 기준점으로 삼고, 같은 연속 브라우징의 다음 잡기마다 그 자리로 되돌린다.
- 다른 label로 옮길 때는 커서를 거기 두고 0.4초 이상 멈춘 뒤 잡아야 한다. 멈추기 전에(커서가 움직이는 중에) 잡으면 이전 자리로 되돌려진다.
- 로그/이벤트: `scroll_return:x,y`, 프레임별 `browse`의 종류 `series`.

## 핀치 브라우징 중 드래그 간섭, 되돌릴 때 반대로 스크롤 (2026-11-04 22:1x 기록)
- **드래그 간섭**: 엄지+검지로 페이지를 잡을 때 중지 끝이 검지 바로 옆(0.022~0.034, 손 크기의 0.2~0.28)에 있어서, 잡은 지 0.25초 안에 엄지+검지+중지 드래그로 바뀌었다. 이 시간대 스크롤 대부분이 드래그로 넘어갔고 중지가 실제로 닿은 적은 없었다. 수정: 세 손가락 드래그는 중지도 손 크기의 0.15 안에 있어야 시작한다(`drag_hold_size_ratio`).
- **되돌림**: 한 번 쓸어 내린 뒤 다음 스크롤을 위해 손을 되돌릴 때, 손가락을 벌리는 중인데 엄지-검지 거리(0.03~0.04)가 놓는 기준(약 0.06)보다 작아서 잡힌 채로 되돌아와 페이지가 반대로 움직였다. 수정: 스크롤 중 엄지-검지가 잡은 동안 가장 가까웠던 거리보다 0.012 넘게 벌어졌고(`scroll_return_open`) 손이 그 쓸기의 끝점에서 0.015 넘게 돌아오면(`scroll_return_distance`) 바로 놓는다. 그 뒤 1초 안에는 손이 계속 되돌아가는 중(쓸기 반대 방향 0.15폭/초 이상, `scroll_return_speed`)이면 다시 잡지 않는다.
- 로그 재생(최근 기록, 정확도 아님): 드래그 시작 13 → 2번, 잡은 채 0.02 넘게 되돌아온 경우 20 → 6번, 되돌림이 곧바로 반대 방향으로 다시 잡힌 경우 2 → 2번. 하루 전체: 드래그 35 → 13, 되돌림 34 → 11. 클릭·창 전환 수는 그대로.
- 시험: 실제 기록 4.7초(`tests/fixtures/scroll_grab_stroke_and_return.json`)에서 드래그가 없고 되돌림이 0.012 미만, 규칙을 끄면 드래그와 0.024 되돌림이 다시 나온다.
