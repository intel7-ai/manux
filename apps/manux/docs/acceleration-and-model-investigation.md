# 학습 가속과 모델 개선 방향 조사

조사 기준일: 2026-11-05. **구현 결과나 채택된 결정이 아닌 제안이다.**
기준 커밋: preview `589cc9a8d338e40df8edc005825caf0c9a6329fc`.
학습 센터 PR [#72](https://github.com/intel7-ai/manux/pull/72)가 병행 진행 중이다.
소스 실행과 설치본 worker에 관한 검증 결과는 병합 후 다시 확인해야 한다.
이 조사는 해당 작업 폴더·계약·학습 코드·모델 저장소를 수정하지 않는다.

## 권고

모듈로 나눈 Qt/Python 앱과 판정기를 교체할 수 있는 경계를 유지한다.
독립된 사용자·세션 평가에서 변경 근거가 나올 때까지 작은 다중 분류 인과 TCN을 기준 모델로 둔다.
우선 학습 라벨과 시범 데이터를 개선하고, 입력부터 실제 명령까지 전체 경로의 오류를 측정한다.
학습 가속은 선택적으로 PyTorch CUDA부터 시제품을 만들고, 다음으로 Intel XPU를 검토한다.
OpenVINO NPU는 별도의 **추론** 실험으로 다룬다. 가속기가 있다는 사실만으로
이 작은 모델의 학습이 더 빨라진다고 판단할 수는 없다.

수용 영역, 즉 한 예측이 참고하는 입력 범위는 `1 + 2*(1+2+4) = 15`프레임이다.
30 fps에서는 약 0.5초, 15 fps에서는 약 1초의 과거를 본다.
이는 **참고하는 이력**이며 매 판정에 무조건 0.5초가 걸린다는 뜻은 아니다.
초기 입력 누적과 실행 확정에는 별도 시간이 필요하다. 실제 손짓 시작부터 명령까지의
지연은 이벤트 시각으로 측정해야 한다.

## 하드웨어 선택지: 학습과 추론은 다른 작업이다

| 하드웨어·실행 환경 | 학습 세션 | 추론 | 우선순위 |
| --- | --- | --- | --- |
| CPU/PyTorch | 현재의 범용 기준 경로 | 현재 ONNX Runtime CPU | 항상 유지할 기준 |
| NVIDIA/PyTorch CUDA | 호환되는 배포 패키지·드라이버를 갖추면 첫 선택적 학습 경로로 적합 | 별도의 ORT CUDA 선택지 | 첫 학습 시제품 [1] |
| 지원되는 Intel GPU/PyTorch XPU | 공식 Windows 학습 예제 있음. 정확한 GPU·드라이버·패키지 조합을 확인해야 함 | OpenVINO Intel GPU 또는 검증한 다른 실행 환경 | 두 번째 학습 시제품 [2] |
| Intel NPU/OpenVINO | 현재 PyTorch 역전파·최적화 반복을 실행할 경로가 아님 | 내보낸 모델을 NPU용으로 컴파일하고 연산 지원·정밀도·지연 검증 | 추론 조사만 진행 [3] |
| 기타 DirectX 12 GPU/torch-directml | Microsoft가 공개 미리보기 단계의 학습을 안내함. 의존성과 연산 호환성은 격리 환경에서 검증 필요 | ORT DirectML 제공. Windows 신규 기능 개발은 WinML로 이동 중 | 실험 단계. 모든 GPU 지원을 약속하지 않음 [4,5] |
| AMD GPU/네이티브 Windows ROCm | 지원 조합이 제한적이며 연결한 Radeon 제약 문서에는 ML 학습 미지원이 명시됨 | 일부 PyTorch 추론 조합 지원 | 장치가 있다는 이유만으로 학습 지원을 안내하지 않음 [6,7] |

OpenVINO는 NVIDIA·AMD까지 통합하는 범용 학습 API가 아니다. Intel GPU와 Intel NPU도
서로 다른 장치다. ONNX Runtime 실행 공급자는 내보낸 계산 그래프를 가속한다.
`Predictor`에 이를 추가해도 학습기의 `loss.backward()`가 빨라지지는 않는다.
TCN을 가속해도 MediaPipe 손 추적이 자동으로 빨라지지 않는다.
위임 장치 열거형이 있다는 사실만으로 Windows MediaPipe GPU 지원을 약속해서는 안 된다.

### 구현 범위 제안

대상은 `tools/`의 학습기·비교 도구·worker, 선택적 패키징, 추론용 `ml`이다.
기능 ID는 `tcn`·`tcn_gate`를 유지한다. 계약 §4·§10(특징·모델), §12(#72 이후의 worker·UI),
구조 §4의 경계를 따른다. 이 조사에서는 계약을 바꾸지 않는다.
실제 구현 PR에서는 계약 문서를 먼저 수정한다.

1. worker가 처리하는 학습 장치 옵션 `auto|cpu|cuda|xpu`를 추가한다.
   설치된 실행 환경, 장치 사용 가능 여부, 대표적인 순전파·역전파·Adam 갱신을 확인한다.
   요청 장치·실제 장치·torch 빌드·CPU로 전환한 이유를 기록한다.
   명시적으로 고른 장치를 쓸 수 없으면 이유와 함께 실패해야 한다.
   `auto`는 이유를 표시하고 CPU를 선택할 수 있다.
   먼저 단일 장치·FP32와 측정으로 확인한 보수적인 선택 정책부터 적용한다.
2. **최적화기 생성 전에** 모델을 장치로 옮기고, 손실 가중치·미니배치·라벨도 일관되게 옮긴다.
   증강 코드의 `rand/ones/zeros`는 배치와 같은 장치·자료형으로 생성한다.
   배치 인덱스와 난수 생성기도 명시적으로 처리한다.
   기존 CPU 경로의 시드 동작은 보존하되, 장치 간 학습 결과가 완전히 같다고 약속하지 않고 시드를 기록한다.
3. 겹치는 모든 입력 구간을 한꺼번에 VRAM으로 옮기지 않는다.
   CPU 데이터 준비·특징 캐시·입력 구간 확장·전송·학습·교차 평가를 나누어 측정한다.
   메모리가 허용되는 경우에만 미니배치 전송과 전체 장치 캐시를 비교한다.
4. `predict`가 모델 장치를 사용하고 결과는 `.cpu().numpy()`로 반환하도록 바꾼다.
   평가 모드의 CPU 복사본과 CPU 예제 입력으로 내보낸다.
   ONNX 결과를 학습 모델과 비교한 뒤 기존의 독립 평가·모델 승격 검증도 그대로 수행한다.
5. 자체 모델·학습 구현이 있는 `compare_tcn.py`와 장치 처리를 공유한다.
   시간 측정 전 준비 실행을 하고, 측정할 가속기의 작업 완료를 동기화한다.
6. #72 병합 뒤 별도 MANUXWorker를 통해 연결한다. 기본 배포는 CPU로 두고
   선택적 실행 환경의 배포는 격리된 환경에서 평가한다.
   호환되지 않는 torch·ORT 배포 패키지를 한 worker에 함께 설치하지 않는다.
   소스 Python 실험만으로 묶음 Windows 실행 파일까지 검증됐다고 판단하지 않는다.
7. 이후 `Predictor` 뒤에 선택적 OpenVINO·ORT 추론 생성기를 시험한다.
   실제 장치를 조회하고 이 ONNX 모델을 컴파일한 뒤 실행 배정과 CPU 전환을 기록한다.
   출력값뿐 아니라 **실제 이벤트**도 비교하고, 최초 컴파일 시간과 준비 실행 후 p95 지연을 측정한다.
   모델 해시·중립 복귀 후 실행 허용·오류 시 안전 초기화를 보존한다.
   개인 모델이 입력을 거절했다고 다른 판정기로 우회하지 않는다.
   AUTO에 의존하지 않고 NPU를 명시적으로 선택해 실제 NPU 실행부터 입증한다.

학습 시제품의 완료 기준 제안은 다음과 같다. CPU와 지원을 주장하는 각 실행 환경에서 같은
독립 평가 절차를 통과하고, 내보낸 모델의 예측 차이가 미리 정한 허용 범위 안에 있어야 한다.
취소·실패 시 사용 중 모델이 보존되고, 깨끗한 환경의 설치본 worker가 실행돼야 한다.
대표 데이터셋에서 **전체 학습 세션** 대기 시간의 중앙값이 의미 있게 줄어야 한다.
임시 최적화 목표는 세 번 실행해 총 대기 시간을 20% 이상 줄이는 것이다.
이는 제안한 개발 판단 기준이며 기존 제품 요구사항이나 측정 결과가 아니다.

## 모델이 사용자 의도를 더 잘 배우게 하는 방법

이 모델에 전달하는 지시는 라벨이다. 손짓 이름만으로 원하는 명령이나 실행 시점이 설명되지는 않는다.
손짓 인식과 손짓→액션 연결을 분리한다. 클릭이라면 중립 → 의도적 핀치 → 손가락 떼기를 시범 보이고,
포인터를 옮기다 우연히 손가락이 닿는 경우도 별도로 보여 주어야 한다.

우선순위는 다음과 같다.

1. **시범과 라벨을 맞춘다.** 안내의 `do` 라벨이 실제 손짓 수행 시점과 일치하는지 확인한다.
   잘못한 시도를 검토·재시도할 수 있게 한다. 카운트다운만으로 라벨이 정확하다고 가정하지 않고
   동작 단계와 시작 시점을 기록한다.
2. **현실적인 비동작 예시를 모은다.** 포인터 이동, 손 쉬기, 긁기, 물건 잡기, 화면에 손 넣기·빼기,
   다른 손가락 접촉, 동작 후 복귀를 포함한다. 학습에서 제외한 전환 구간도 평가한다.
   새 라벨을 추가하거나 특징 계약을 바꾸기 전에 전환·거절 정책을 명시적으로 시험한다.
3. **독립적인 변화를 확보한다.** 녹화 시도·세션·사람을 나누고 속도·거리·조명·손 방향·자세·카메라를 바꾼다.
   관절 좌표를 합성 증강해도 실제 영상의 가림이나 추적 실패를 재현할 수는 없다.
4. **오류를 골라 교정한다.** “방금 잘못됐어요” 표시는 사람이 확인할 어려운 정답·비동작 후보를 고르는 데 쓴다.
   모든 표시를 자동 재라벨링·학습에 넣은 뒤 같은 예시를 독립 평가로 다시 쓰지 않는다.
5. **검증 데이터로 실행 정책을 조정한다.** 허용 오실행 수준을 고정하고 클래스별 임계값·모호함 여유값·
   중립 복귀 조건·단계별 시간을 비교한다. 최종 독립 시험 전에 설정을 고정한다.
   최종 시험 결과에 맞춰 설정을 반복 조정하지 않는다.
6. **그다음 특징과 모델을 비교한다.** 거리·각도 기반 기준 모델이나 작은 MLP, 현재 TCN을 비교한다.
   시간 관련 오류가 남으면 더 긴 입력이나 시간 정규화를 적용한 TCN, 작은 GRU를 시험한다.
   특징 값이 바뀌면 특징 버전을 올린다. 사전학습된 손동작 시퀀스 인코더가 필요한 예시를 줄일 가능성은 있다.
   그러나 기존 두 동작의 고정 특징 추출부 실험 실패는 그런 사전학습의 평가가 아니다.
   Transformer·RGB 모델은 더 크다는 이유가 아니라 측정된 필요성과 충분한 독립 데이터가 있을 때 검토한다.

나중에 LLM이 설정을 설명하거나 사용자 문장을 검토된 동작 목록·바인딩에 연결하도록 도울 수는 있다.
그러나 누락된 손 관절을 복원하거나, 잘못된 시범 라벨을 저절로 교정하거나,
실시간 명령·해제의 결정적 제어를 대신하지는 못한다.

## 사용자가 수집 순서를 따르지 않을 때의 데이터 품질 위험

**위험도는 높다. 다만 발생 빈도는 아직 측정하지 않았다.** 현재 수집 절차는 “안내한 동작을
사용자가 그 시점에 수행했다”는 가정에 의존한다. 파일이 정상적으로 저장됐거나 손 관절이
유효하다는 사실은 라벨이 맞다는 증거가 아니다. 학습과 평가에서 같은 방식으로 잘못 수행하면
내부 점수까지 좋아 보일 수 있다. GPU는 잘못된 데이터의 학습을 빠르게 할 뿐 이를 고치지 않는다.
라벨의 근거와 사람의 확인이 필요하다는 원칙은 [Google의 라벨 안내][9], 독립 그룹 평가의
필요성은 [scikit-learn의 그룹 교차 검증 안내][10]와도 일치한다.
아래 위험·대응은 현재 코드에서 도출한 분석과 **후속 구현 제안**이며 실측 결과가 아니다.

### 현재 보호 장치와 남아 있는 빈틈

- `data/guided.py:GuidedSession.label`은 실제 동작의 정답을 확인하지 않고 시간표에 따라
  `prep→transition`, `do→지정 클래스`, `rest→none`을 기록한다. `label_delay`와 `settle`은
  일부 전환 시간을 제외하지만 개인별 반응 지연이나 쉬는 동안의 동작 지속을 보장하지 못한다.
- `GuidedSession.update(available=False)`와 일시정지는 타이머를 멈추고 해당 프레임을 학습에서 뺀다.
  이는 추적 소실 방지책이며, 다른 손 모양이 또렷하게 추적되는 경우를 걸러내지는 못한다.
- `tools/collect_mouse.py:Take.finish`는 반복별 유효 관절 프레임 수를 확인한다.
  현재 CLI 기준은 반복 동작당 최소 3프레임, 자유 동작은 15프레임이다.
  이는 완료 파일의 최소 사용 가능성 검사이지 올바른 동작·충분한 다양성·시도 품질의 보장은 아니다.
  #72의 앱 수집 경로까지 같은 검사가 적용되는지는 병합 후 별도로 확인해야 한다.
- `capture_plan.condition_key`는 사용자가 선택한 조건의 해시다. 실제 거리·조명·자세를 측정한
  증거가 아니다. 같은 자세로 모든 안내를 넘겨도 서로 다른 조건 그룹으로 기록될 수 있다.
- `tcn_data.load`는 완료·손상 여부, 지정한 split과의 일치, preset 혼합 등을 검사한다.
  학습 경로는 split이 없는 이전 녹화를 허용하므로 새 수집과 구버전 호환 정책도 구분해야 한다.
- `promote_tcn.validate_and_install`은 명시적 `split=eval`, 학습 파일과의 SHA256 중복,
  평가 중 파일 변경을 확인한다. 바이트가 다른 재포장·복제 구간이나 같은 세션의 강한 유사성,
  잘못 수행한 평가 라벨까지 증명하지는 못한다. **교체 검증도 평가 데이터의 품질에 의존한다.**

개인화에서 사용자가 일관되게 다른 자세를 쓰는 것은 반드시 오류가 아니다.
“카탈로그 동작을 재현하는 수집”과 “사용자가 새 동작을 정의하는 수집”을 구분해야 한다.
후자는 별도 동작 ID·설명·바인딩·검증으로 다뤄야 하며 기존 클래스에 몰래 섞으면 안 된다.
장애·신체 차이로 표준 시범을 따라 하기 어려운 경우도 같은 원칙을 적용한다.

### 개선안: 수집 전·도중·완료 후에 나눠 적용

1. **P0 — 학습 전 이해를 확인한다.** 동작 하나의 짧은 예시와 “이렇게 하면 안 됨” 예시를
   함께 보여 주고, 2~3회의 저장하지 않는 연습 뒤 사용자가 시작하게 한다.
   시각·음성 신호와 준비 시간을 선택할 수 있게 하고, 뒤로 가기·잠시 멈추기·이번 시도 다시 하기를 제공한다.
   고정 숫자는 초기 사용성 실험안이며 검증된 최적 횟수가 아니다.
2. **P0 — 완료와 품질을 분리해 표시한다.** “파일 저장 완료”와 “라벨 확인됨”을 별도로 표시한다.
   추적 유효 비율·연속 관절 누락·시도 길이·프레임 시간 공백·중립 노출·조건별 시도 수를 요약한다.
   손이 보인다는 이유만으로 “올바른 동작”이라고 표시하지 않는다.
   원시 영상 저장 없이 실시간 미리보기와 관절 재생으로 사용자가 실패 시도를 확인·제외하게 한다.
   관절 재생만으로 가림이나 실제 의도까지 복원할 수 없으므로 애매하면 재수집한다.
3. **P0 — 잘못된 시도만 다시 받는다.** 잘못 수행·불확실·추적 불량을 구분해 보류한다.
   전체 녹화를 지우거나 사용 중 모델을 바꾸지 않고 해당 시도·조건만 다시 수집한다.
   원본을 덮어쓰지 않으며 학습에 채택한 시도 목록과 제외 이유를 별도로 관리한다.
4. **P0 — 평가의 독립성을 사용자 흐름으로 만든다.** 학습 뒤 새 평가 세션을 안내하고
   다른 시점·순서의 시도를 받는다. 사람·세션·원본 시도 단위로 나눈 뒤 입력 구간을 만든다.
   같은 세션을 잘라 train/eval로 나누거나 인접 프레임을 무작위 분할하지 않는다.
   최초 기본 모델은 새로운 사람, 개인 모델은 같은 사람의 새로운 세션을 주요 평가 대상으로 구분한다.
5. **P1 — 관측 가능한 것만 자동 확인한다.** 화면 위치·손 크기·움직임·손끝 거리 등으로
   시간표와 크게 어긋나는 구간을 의심 후보로 제시할 수 있다.
   단일 카메라의 손 크기만으로 실제 30/60/100cm를 인증하거나 손 관절만으로 조명을 인증하지 않는다.
   새 손짓을 배우는 중이므로 기존 규칙·모델과 다르다는 이유만으로 강제 탈락시키지 않는다.
   규칙 불일치는 검토 신호이지 정답이 아니며 자동 라벨 변경의 근거로 쓰지 않는다.
6. **P1 — 데이터 계보와 공유 경계를 둔다.** 향후 세션·시도 식별자, 원본/파생 관계,
   확인 상태·제외 이유·수집기 버전을 계약에 먼저 정의한다.
   정확 파일 해시에 더해 메타데이터를 제외한 내용 중복과 근사 중복을 검토한다.
   같은 동작의 자연스러운 반복을 중복으로 오인할 수 있으므로 근사 검사는 경고·검토용이다.
   확인 전 녹화는 자동 팀 학습에 합치지 않고, 현재 명시적 업로드 원칙을 유지한다.
   업로드 성공·해시 일치는 데이터의 정답성을 보증하지 않는다.
7. **P2 — 강건한 학습 기법은 보조로 비교한다.** 시도 단위 가중치 제한, 클래스·세션별 균형,
   라벨 잡음에 강한 손실 등을 깨끗한 기준 데이터와 비교할 수 있다.
   높은 손실·모델 불일치만으로 특이한 사용자의 올바른 시범을 자동 삭제하지 않는다.
   오염 데이터를 가리는 기법보다 명확한 안내·검토·재수집을 먼저 적용한다.

표시할 품질 지표의 초기 예는 “저장 10시도, 사용자 확인 8시도, 재수집 권고 2시도,
중립 노출 40초, 실제 조건 확인 안 됨”이다. 이는 화면 제안이며 현재 구현이 아니다.
진단 정보는 `data/tools`가 계산하고 UI는 결과를 표시한다. 녹화 형식·상태·worker 응답이
바뀌면 계약 §9·§12와 필요 시 형식 버전을 먼저 수정한다. 개인정보·원시 영상은 추가하지 않는다.

### 품질 대책 자체를 검증하는 실험

- 깨끗하게 별도 확인한 데이터를 고정한 뒤, **복사한 실험용 학습 데이터만** 오염시킨다.
  동작 라벨 바꾸기, 시작 시점 이동, 중립에 동작 섞기, 조건 허위 기록,
  특정 클래스 누락·편중, 같은 원본의 재포장 중복을 각각 따로 시험한다.
  학습 라벨 오염 비율 0/5/10/20%와 시작 시점 ±0.2/0.5초는 탐색용 예시이며
  실제 사용자 오류율이나 안전 임계값을 뜻하지 않는다.
- 깨끗한 독립 평가로 시도 적중·잘못된 명령·중립 오실행·지연·승격 거절 여부를 측정한다.
  별도의 실험에서는 평가 데이터도 오염시켜 승격 장치가 잘못 승인하는지 확인한다.
  이 실험용 결과를 실제 모델 설치에 사용하지 않는다.
- 초보자가 안내를 오해하는 상황을 관찰하고 개선 전후의 라벨 오류·재수집률·소요 시간·중도 포기를 비교한다.
  자동 경고의 탐지율뿐 아니라 **정상 시도를 잘못 거절하는 비율**도 확인한다.
  합성 오류 실험만으로 실제 사용자의 준수율을 입증했다고 보고하지 않는다.
- 허용할 오류·거절·부담 수준은 실제 예비 평가 후 정한다.
  최종 정답 확인이 부족하거나 독립 평가를 구성할 수 없으면 “검증 불가”로 남기고 기존 모델을 보존한다.

핵심은 사용자가 절차를 완벽히 따른다고 가정하는 대신, 실수하기 쉬운 안내를 줄이고
**확인 가능한 품질·사람의 검토·독립 평가·안전한 재수집**을 수집 흐름에 넣는 것이다.

## 현재 아키텍처를 계속 추진할 가치가 있는가?

**앱 구조는 유지할 가치가 있다.** 판정기 인터페이스, 재생 가능한 관측값, 손짓·액션 분리,
단일 Windows 출력 경계, 불변 Snapshot, 원자적 모델 승격 덕분에 대안을 비교할 수 있다.
현재 인식 문제에서 Qt와 다른 UI의 차이가 병목이라는 근거는 없다.
무거운 학습은 별도 worker에서 처리하고 엔진은 프레임을 쌓지 않고 최신 프레임을 계속 처리해야 한다.

**모델 구조는 합리적인 기준이지만 아직 입증되지 않았다.** 인과 시간 합성곱은
시퀀스 모델링의 출발점으로 연구된 방식이다[8]. 해당 논문이 현재의 작은 구현이나
웹캠 제어를 검증한 것은 아니다. 한 사람의 결과로 사람·조명·카메라가 달라져도
견고하다고 결론 내릴 수는 없다. 독립 이진 모델에도 공통 중재와 새 동작의 비동작 예시가 필요하다.
모델 파일 하나를 추가한다고 서로 다른 동작의 오실행이 사라지지는 않는다.

| 독립 평가에서 관찰한 현상 | 다음 조사 방향 |
| --- | --- |
| 어두운 곳이나 목표 거리에서 세계 좌표가 없거나 불안정함 | 입력·추적·카메라 배치 개선. 목표 환경에서 계속 관측 불가능할 때 다른 센서 검토 |
| 관절은 안정적인데 손 모양을 혼동함 | 라벨·비동작 예시·구별에 필요한 특징 개선. 단순 기준 모델과 TCN 비교 |
| 손 모양은 맞지만 시작·해제·반복 실행이 틀림 | 동작 단계·실행 허용·상태 정책·시간 맥락 개선. 전체 엔진 재생 |
| 재생은 맞는데 실제 과제가 불안정함 | 추적 지연·프레임 간격·통합·피드백·사용 자세 확인 |
| 인식은 되지만 재학습이 느림 | 학습 하드웨어 추가 전 교차 평가·데이터 준비 시간 분석 |
| 책상에서는 되지만 누워서는 못 씀 | 상호작용과 카메라 배치를 재검토. 책상 점수만으로 최종 사용 환경을 검증하지 않음 |

## 현재 앱 시험으로 방향을 찾으려면

1. **시험 빌드를 고정한다.** #72 이후 정확한 커밋·설치본·추적기·모델·설정·바인딩·장치를 기록한다.
   실제 OS 과제 전에 연습·출력 없음 상태의 기본 동작을 확인한다.
   일시정지·손 소실·취소·모델 교체 시 눌린 입력의 해제를 확인한다.
2. **작은 예비 평가를 한다.** 3~5명이 자기 카메라로 서로 다른 시점에 최소 두 세션을 수행한다.
   학습·설정 조정용 검증·최종 평가 시도를 분리한다.
   이는 초기 방향을 찾는 규모이며 출시 검증에 충분한 표본이라는 뜻이 아니다.
   책상뿐 아니라 목표로 하는 누운 자세의 거리·조명도 포함하되 모든 요인을 한 번에 바꾸지 않는다.
3. **정해진 과제를 수행한다.** 표적까지 포인터 이동, 클릭·더블클릭, 끌어 놓기, 스크롤,
   모드 변경, 긴 중립·일상 손 움직임, 손 재진입을 포함한다.
   일반 마우스로 같은 기준 과제를 수행하고 편안함·피로·설정·학습 부담도 기록한다.
4. **같은 입력을 짝지어 재생한다.** 같은 독립 평가 관절 기록을 규칙, 규칙+TCN 확인기,
   직접 TCN에 넣고 바인딩·설정을 맞춘다. 연습 출력으로 발생 명령을 기록한다.
   사람·조건별 시도 수, 잘못된 명령, 놓침, 중복 명령, 중립 노출 시간, 해제 누락·지연을 보고한다.
   분류기만 평가하는 `evaluate_tcn.py`는 유용하지만 전체 경로 비교를 대신하지 못한다.
5. **실제 사용으로 확인한다.** 판정기 시험 순서를 교차 배치하고 과제 성공·시간·복구,
   의도하지 않은 OS 명령, 손짓 시작→명령 지연의 중앙값·p95를 측정한다.
   추적 소실과 프레임의 오래된 정도는 TCN 처리 시간과 따로 기록한다.
   관절 재생은 추적 이후부터 시작하므로 카메라·추적기 대안을 비교할 수 없다.
6. **하드웨어 성능을 측정한다.** 소규모·중규모·증가한 데이터셋에서 각각 세 번 실행한다.
   캐시 없음·있음, 에포크·교차 평가·시드를 맞추고 실제 CPU·CUDA·XPU를 비교한다.
   동시 학습으로 비교가 왜곡되지 않도록 실행 환경을 분리한다.
   총 경과 시간·메모리·내보내기·모델 승격 성공·학습 중 앱 반응성을 기록한다.
   TCN의 CPU·NPU 추론과 카메라→명령 지연은 별도로 측정한다. 이번 조사에서 가속 효과를 실측하지는 않았다.

최종 평가 전에 중립 1분당 오실행, 동작별 시도 적중률, p95 지연, 과제 완료율,
피로의 허용 수준을 합의한다. 중립 10분 동안 오실행이 0건이어도 근거는 약하다.
발생률이 일정한 포아송 과정이라고 가정하면 단측 95% 상한은 대략 `3 / 노출 시간(분)`이다.
이 가정 아래 30분간 0건이면 상한은 약 0.1건/분이다.
서로 연관된 오류와 사람·조건 차이는 따로 보고해야 한다.
버튼이 눌린 채 남거나 안전 해제가 누락되면 전체 정확도와 무관하게 출시를 막아야 한다.

먼저 **어느 단계가 실패하는지** 판단한 뒤 모델·하드웨어 변경을 고른다.
현재 앱은 단계가 분리돼 있어 시험으로 방향을 찾을 수 있다.
단일 “정확도” 수치만 보면 오히려 그 방향이 가려진다.
