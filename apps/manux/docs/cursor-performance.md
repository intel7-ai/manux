# 커서 버벅임: 추적 수 기본값 회귀와 확인 방법

2026-11-05. 사용자 보고: 전날보다 커서 움직임이 크게 버벅임. 이전 설치본 번호·모드는 확인되지 않았다.
따라서 아래 결과로 사용자의 지연 원인 전체가 확정됐다고 주장하지 않는다.

## 확인한 차이와 이번 수정

이전 v0.3의 `hand-mouse/src/hand_tracker.py`는 기본 `num_hands=1`이다.
v0.4의 `tracking/landmarker.py`는 기본 2였고 앱 조립 지점에서 이를 바꾸지 않았다.
한 손으로 조작할 때도 두 번째 손을 찾는 비용이 생길 수 있다.
MediaPipe의 [Hand Landmarker 그래프 구현](https://github.com/google-ai-edge/mediapipe/blob/master/mediapipe/tasks/cc/vision/hand_landmarker/hand_landmarker_graph.cc)에는
추적 중인 손 수가 목표에 도달했는지에 따라 손 검출을 생략하는 경로가 있다.

기본값을 1로 복원하고 `tracking.num_hands` 설정으로 2를 명시할 수 있게 했다.
선택한 조작 손이 없으면 기존처럼 명령을 내지 않는다. 한 손 설정에서는 조작할 손만 보여 준다.
이번 수정에서는 포인터 감도·EMA·커서 보간·명령 해제 정책을 바꾸지 않았다.

## 통제된 CPU 측정

- 입력: [MediaPipe 공식 thumbs_up.jpg](https://storage.googleapis.com/mediapipe-tasks/gesture_recognizer/thumbs_up.jpg).
  개인 영상·웹캠을 사용하지 않았고 사진을 저장소에 추가하지 않았다.
- 현재 번들 모델, 같은 PC·실행 환경·사진, 전체 영상 경로, 확대 끔.
- 검출 수 1/2/2/1/1/2 순서로 각각 새 검출기를 만들고 준비 15회 후 85회 측정했다.
  모든 측정 구간에서 검출된 실제 손은 1개였다.

| 설정 | 각 실행의 중앙값(ms) | 각 실행의 p95(ms) |
| --- | --- | --- |
| 최대 1개 손 | 15.929 / 14.760 / 13.991 | 21.570 / 22.479 / 15.691 |
| 최대 2개 손 | 33.523 / 31.451 / 30.957 | 46.647 / 59.468 / 46.239 |

이 조건에서는 2개 설정의 처리 시간이 약 두 배였다. 이는 정지 사진 반복 처리 비용이며
실제 카메라 FPS·인식률·손짓→화면 지연이나 사용자의 체감 개선률은 아니다.

## 새 진단 표시

기존 FPS·추론 시간 옆에 **앱 내 프레임 지연**을 표시한다.
앱이 프레임을 받은 시각부터 처리 후 상태 발행 직전까지의 시간이며,
카메라 드라이버 내부 버퍼·화면 표시 지연은 포함하지 않는다.
추론 시간과 앱 내 전체 지연을 구분하기 위한 값이지 실제 반응 시간의 완전한 측정은 아니다.

## 실제 PC에서 다음에 확인할 것

1. 같은 카메라·모드·조명·거리·감도로 비교하고 학습·다운로드가 실행 중인지 기록한다.
2. FPS·추론 시간·앱 내 프레임 지연을 함께 확인한다.
3. 앱 내 지연은 낮은데 커서가 느리거나 계단처럼 보이면 출력 경로를 별도로 비교한다.
   이전 버전의 One Euro 떨림 보정·144Hz 보간·검지 모드 배율은 현재 출력 경로와 차이가 있다.
   보간은 부드러움과 지연 사이의 절충이므로 원인 구분 없이 한꺼번에 추가하지 않는다.
4. 낮은 FPS에서 `reanchor_gap`을 넘는 프레임 간격 때문에 이동이 자주 재시작하는지도 확인한다.
   이를 피하려고 안전 초기화나 손 소실 해제를 무작정 늦추지 않는다.
5. 지연이 남으면 실제 카메라·입력·출력 구간별 측정으로 다음 수정을 정한다.

별명 입력·녹화 안내·허브 읽기/쓰기 상태 수정은 PR #75의 별도 변경이며,
커서 성능 수정은 그 뒤의 변경이다. 설치본을 비교할 때 버전을 구분한다.
